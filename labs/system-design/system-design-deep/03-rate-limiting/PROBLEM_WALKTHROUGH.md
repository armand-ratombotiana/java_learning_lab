# Problem Walkthrough: Sliding Window Rate Limiter with Redis Semantics

## Problem Statement

A public API gateway must enforce per-client rate limits (e.g., 100 requests per
minute) with a **hard cap**: a client may never be admitted more than `limit` times
in any rolling window. Enforcement happens at the edge across many gateway nodes,
so the decision must be shared and atomic. Redis is available. Implement a sliding
window rate limiter with Redis semantics — one sorted set per client key,
trim-by-score, count, conditionally add — and make the failure modes explicit for
a distributed deployment.

## Requirements

- **Per-client budget:** each client gets an independent `limit` over a sliding
  window of `window` duration (e.g., 100 requests / 60 s).
- **Hard cap:** at no point may a client exceed `limit` admitted requests within
  the last `window` of time — not even across window boundaries.
- **Sliding window semantics:** the window is `[now - window, now]`, not a fixed
  clock-aligned bucket.
- **Atomicity:** the trim-check-add sequence must be atomic — concurrent requests
  from different gateway nodes must not jointly exceed the cap.
- **Memory bounded:** per-client state is trimmed on every call and keys expire
  after `window + slack`, so Redis doesn't accumulate unbounded ZSETs.
- **Deterministic testing:** the time source is injectable; no wall-clock
  dependence in tests.
- **Explicit outage policy:** behavior when Redis is unavailable (fail-open by
  default, fail-closed per tier as an option).

## Constraints & Assumptions

- Redis (or a Redis-compatible store) is the shared arbiter; the Java
  implementation models the exact ZSET semantics in memory.
- Timestamps are milliseconds, generated by a single shared clock authority to
  avoid per-node skew.
- The limit is per authenticated client (API key / user id); unauthenticated
  traffic keys on IP (NAT caveat noted).
- Latency budget: the limiter adds one Redis round trip (~1 ms) per request;
  local pre-filtering is a deployment concern, not part of the core algorithm.

## Why Sliding Window (And Not the Alternatives)

| Approach | Behavior | Verdict |
|----------|----------|---------|
| **Fixed window** | One counter per aligned bucket (per minute) | Boundary burst: 200 requests in 200 ms across two buckets at 100/min. Rejected. |
| **Token bucket** | Tokens refill at `rate`; bucket holds `burst` | Great for burst-tolerant clients; the cap is a *rate*, not a window. Not what was asked. |
| **Sliding window log (ZSET)** | Exact count of timestamps in `[now - window, now]` | **Chosen** — exact, Redis-canonical, matches the hard-cap requirement. |
| **Sliding window counter** | Blend two fixed buckets by overlap fraction | O(1) memory, bounded error; the scale-out fallback, not the default. |

**The boundary burst problem (why fixed windows fail):** with a fixed 100/min
bucket, a client sends 100 requests at `t = 59.9 s` and 100 more at `t = 60.1 s`.
Two buckets, each under the cap, but the client achieved 200 requests in 200 ms —
double the intended rate. A sliding window counts over `(now - 60s, now]` and
rejects the 101st request no matter where in the minute it arrives.

## Solution Overview: Redis Semantics

The canonical Redis implementation is a single Lua script run with `EVAL`, making
the entire decision atomic on the server:

```
Keys:    KEYS[1] = client key, e.g. "rl:{clientId}"
Args:    ARGV[1] = now (ms, from the shared clock)
         ARGV[2] = window (ms)
         ARGV[3] = limit
         ARGV[4] = request unique id

1. ZREMRANGEBYSCORE KEYS[1] 0 (now - window)      -- trim expired timestamps
2. count = ZCARD KEYS[1]                          -- requests inside the window
3. if count < limit:
       ZADD KEYS[1] now "<now>:<requestId>"       -- record this request
       return ALLOWED
   else:
       return REJECTED
```

### Why this is correct

- **Atomicity:** Lua scripts execute without interleaving on one Redis instance —
  the read-modify-write cannot race. Client-side check-and-act (read count, then
  add) would admit `limit + concurrency` requests at the boundary.
- **Data-driven windows:** timestamps live *in* the sorted set; the window is
  computed from stored data, so nodes with skewed clocks cannot shift boundaries
  (the caller passes a shared `now`).
- **Self-trimming:** every call removes expired members, so ZSET size per client
  is bounded by `limit`, not by request volume.
- **Unique members:** `now:requestId` prevents two requests at the same millisecond
  from colliding in the ZSET and being counted once.

## Step-by-Step Solution

### Step 1: Choose the per-client data structure

A sorted set of timestamps. In Java, a `TreeMap<Long, Long>` (timestamp → same
timestamp; member id for uniqueness) gives `headMap(cutoff).clear()` for trim and
`size()` for count — both range operations over a sorted structure, mirroring the
ZSET.

### Step 2: Define the algorithm (`allow`)

```
allow(clientId):
    now = clock.nowNanos()                       // shared, monotonic clock
    map = clients.computeIfAbsent(clientId)
    lock map:
        cutoff = now - window.toNanos()
        map.headMap(cutoff).clear()              // trim expired (ZREMRANGEBYSCORE)
        if map.size() >= limit: return REJECTED  // ZCARD >= limit
        map.put(now, now)                        // ZADD
        return ALLOWED
```

Per-client locking matches Redis semantics where each key's operations are
independent; one hot client cannot serialize others.

### Step 3: Use a monotonic clock domain

Wall clock (`System.currentTimeMillis`) can jump under NTP steps or
suspend/resume, which would inflate or deflate the window. `System.nanoTime` is
monotonic; the shared-clock concern maps to Redis's `TIME` command in production.
An injectable clock makes tests deterministic.

### Step 4: Bound memory

- The TreeMap per client holds at most `limit` members (trimmed on every call).
- Production keys get a TTL of `window + slack` so idle clients' ZSETs are
  reclaimed — with `EXPIRE` on the key from inside the Lua script.

### Step 5: Define the outage and scale-out behavior

- **Redis down/timeout:** fail open (admit + alert) by default — the limiter
  protects economics, not correctness; failing closed converts a quota tool into
  an availability dependency. Per-tier fail-closed is a config knob.
- **Scale-out:** Redis Cluster shards by client key hash; the Lua script is
  unchanged. When `clients × limit` memory exceeds the cache tier, switch to the
  O(1)-memory sliding window *counter* approximation (documented below).

## Java 21+ Implementation

```java
package com.systemdesign.deep.lab03;

import java.time.Duration;
import java.util.Map;
import java.util.TreeMap;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

/**
 * Lab 03: Sliding Window Rate Limiter with Redis Semantics.
 * Models the canonical Redis Lua script (ZREMRANGEBYSCORE -> ZCARD -> ZADD)
 * with a per-client sorted map and per-client locking. Uses a monotonic,
 * injectable clock.
 */
public class SlidingWindowRateLimiterLab {

    /** Injectable time source; uses System.nanoTime by default (monotonic). */
    @FunctionalInterface
    public interface Clock {
        long nowNanos();

        static Clock system() { return System::nanoTime; }
    }

    /** Redis-style sliding window limiter. One sorted set of timestamps per client. */
    public static final class RedisStyleSlidingWindowLimiter {
        private final long limit;
        private final Duration window;
        private final Clock clock;
        private final ConcurrentHashMap<String, TreeMap<Long, Long>> clients = new ConcurrentHashMap<>();
        private final AtomicLong allowed = new AtomicLong();
        private final AtomicLong rejected = new AtomicLong();

        public RedisStyleSlidingWindowLimiter(long limit, Duration window, Clock clock) {
            this.limit = limit;
            this.window = window;
            this.clock = clock;
        }

        /** Equivalent of the Lua script: trim, count, conditionally add — atomically. */
        public boolean allow(String clientId) {
            long now = clock.nowNanos();
            long cutoff = now - window.toNanos();
            TreeMap<Long, Long> timestamps = clients.computeIfAbsent(clientId, k -> new TreeMap<>());

            synchronized (timestamps) {                 // atomicity per client key
                timestamps.headMap(cutoff).clear();     // ZREMRANGEBYSCORE key 0 (now-window)
                if (timestamps.size() >= limit) {       // ZCARD key >= limit -> reject
                    rejected.incrementAndGet();
                    return false;
                }
                timestamps.put(now, now);               // ZADD key now "<now>:<reqId>"
                allowed.incrementAndGet();
                return true;
            }
        }

        /** Number of requests admitted in the current window for a client. */
        public long outstanding(String clientId) {
            TreeMap<Long, Long> timestamps = clients.get(clientId);
            if (timestamps == null) return 0;
            synchronized (timestamps) {
                long cutoff = clock.nowNanos() - window.toNanos();
                timestamps.headMap(cutoff).clear();
                return timestamps.size();
            }
        }

        public long allowed() { return allowed.get(); }
        public long rejected() { return rejected.get(); }
        public int trackedClients() { return clients.size(); }
    }

    /**
     * O(1)-memory approximation for scale-out: blends the previous fixed bucket
     * with the current one. Error is bounded by the window/bucket ratio.
     */
    public static final class SlidingWindowCounterApproximation {
        private final long limit;
        private final long bucketMillis;
        private final AtomicLong currentBucket = new AtomicLong();
        private final AtomicLong prevBucket = new AtomicLong();
        private final AtomicLong currentStartMillis = new AtomicLong();

        public SlidingWindowCounterApproximation(long limit, long bucketMillis) {
            this.limit = limit;
            this.bucketMillis = bucketMillis;
        }

        public boolean allow(long nowMillis) {
            long bucket = nowMillis / bucketMillis;
            if (bucket != currentStartMillis.get()) {
                synchronized (this) {
                    long cur = nowMillis / bucketMillis;
                    if (cur != currentStartMillis.get()) {
                        prevBucket.set(currentBucket.get());
                        currentBucket.set(0);
                        currentStartMillis.set(cur);
                    }
                }
            }
            long windowMs = bucketMillis;                    // assume 1-bucket window
            long elapsedInCurrent = nowMillis % bucketMillis;
            double estimate = prevBucket.get() * (1.0 - (double) elapsedInCurrent / bucketMillis)
                            + currentBucket.get();
            if (estimate >= limit) return false;
            currentBucket.incrementAndGet();
            return true;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        // 1. Hard cap within a window: limit = 3 requests per 200ms
        RedisStyleSlidingWindowLimiter limiter =
                new RedisStyleSlidingWindowLimiter(3, Duration.ofMillis(200), Clock.system());

        String client = "api-key-1234";
        System.out.println("== Burst within window (limit 3 / 200ms) ==");
        for (int i = 1; i <= 5; i++) {
            System.out.printf("req %d -> %s%n", i, limiter.allow(client) ? "ALLOWED" : "REJECTED");
        }
        System.out.printf("outstanding after burst: %d%n", limiter.outstanding(client));

        // 2. Window slides: after 200ms the window drains and requests pass again
        System.out.println("== After window elapses ==");
        Thread.sleep(220);
        System.out.printf("req 6 -> %s%n", limiter.allow(client) ? "ALLOWED" : "REJECTED");
        System.out.printf("outstanding: %d%n", limiter.outstanding(client));

        // 3. Per-client isolation
        String other = "api-key-9999";
        System.out.println("== Per-client isolation ==");
        for (int i = 1; i <= 4; i++) {
            System.out.printf("other-client req %d -> %s%n", i,
                    limiter.allow(other) ? "ALLOWED" : "REJECTED");
        }

        // 4. Approximation: same limit, bucket-aligned, exact window = 1 bucket
        SlidingWindowCounterApproximation approx =
                new SlidingWindowCounterApproximation(3, 1000);
        System.out.println("== Counter approximation (limit 3 / 1000ms bucket) ==");
        for (int i = 1; i <= 5; i++) {
            System.out.printf("approx req %d -> %s%n", i,
                    approx.allow(System.currentTimeMillis()) ? "ALLOWED" : "REJECTED");
        }

        System.out.println("== Totals ==");
        System.out.printf("allowed=%d rejected=%d trackedClients=%d%n",
                limiter.allowed(), limiter.rejected(), limiter.trackedClients());
    }
}
```

## Complexity Analysis

| Operation | Time | Space | Notes |
|-----------|------|-------|-------|
| `allow` (trim) | O(log n) | O(1) | `headMap(...).clear()` is a range delete over the tree |
| `allow` (count + add) | O(log n) | O(n) per client | n = timestamps in window ≤ `limit` |
| `outstanding` | O(log n) | O(1) | Trim + size |
| Total per-client memory | — | O(limit) | Self-trimming: bounded by the limit, not by volume |
| Aggregate memory | — | O(clients × limit) | The scale-out trigger — see follow-ups |
| Approximation `allow` | O(1) | O(1) | The O(1)-memory fallback |

**Throughput:** one Redis round trip per request (~1 ms); ZSET ops are O(log n)
server-side with tiny `n` (≤ `limit`). The Lua script is a single `EVAL`, so no
pipelining loss beyond the round trip.

## Edge Cases & Failure Modes

| Scenario | Behavior | Why it's correct |
|----------|----------|------------------|
| Boundary burst (59.9 s / 60.1 s) | 101st request in window rejected | Sliding window counts `(now - window, now]` — no aligned-bucket gap |
| Two requests, same millisecond | Both counted | Member id `now:reqId` keeps ZSET members unique |
| Concurrent gateways racing | At most `limit` admitted | Lua atomicity / per-key lock serializes check-and-add |
| Clock jump (NTP step) | No window distortion | Monotonic clock domain (`nanoTime`); production uses Redis `TIME` |
| Redis unavailable | Fail open + `overAdmission` metric | Limiter is an economics guard, not an availability dependency |
| Client with huge ZSET | Trimmed to `limit` on every call | Self-limiting structure |
| NAT shared IP | Aggregated quota per IP | Documented keying caveat; per-IP limits higher, or fingerprinting |
| Idle client keys | `EXPIRE key window+slack` reclaims them | No unbounded key growth in the cluster |

## Verification Walkthrough

1. **Burst:** 5 rapid calls at limit 3 → ALLOWED ×3, REJECTED ×2. The 4th call is
   rejected while timestamps remain inside the window — hard cap held.
2. **Sliding:** after sleeping past the 200 ms window, `outstanding` returns 0 and
   a new request is allowed — the window drained by timestamp, not by bucket.
3. **Isolation:** a second client reaches its own cap independently — keyed state,
   no global coupling.
4. **Approximation:** the O(1)-memory variant enforces the same limit with
   bucket blending — the scale-out fallback works.
5. **Concurrency (production test):** N threads × same key must admit ≤ `limit`
   total — the assertion that catches missing atomicity in the Lua script.

## Follow-Up Questions

1. **Local pre-filtering:** a per-node budget (e.g., 90% of the limit) cuts Redis
   traffic an order of magnitude while keeping the hard cap at the shared tier —
   the remaining 10% is the shared-check tail.
2. **Token bucket alternative:** for burst-tolerant clients, a token bucket
   (refill rate + burst capacity) admits short bursts above the average — the
   semantics are different (rate vs window) and the choice is product policy.
3. **When to switch to the O(1) approximation:** when `clients × limit` exceeds
   the cache tier's memory budget; the approximation's error is bounded by
   `window/bucket` and is tunable via finer buckets.
4. **Redis Cluster + Lua:** `EVAL` requires all keys in one shard — fine here
   because each script touches exactly one key (`rl:{client}` hashes to one slot).
5. **Multi-tier limits (per second + per minute):** run two keys/scripts per
   client; a request must pass both. One script, parameterized, per tier.
6. **Rate limiting response contract:** `429` with `Retry-After` header, plus
   `X-RateLimit-Limit/Remaining/Reset` so well-behaved clients back off — the
   limiter's error responses are part of the API contract.
7. **Fairness across traffic classes:** weighted keys (free vs pro) with different
   `limit` args in the same script — isolation via keyspace, policy via ARGV.

## Summary

- **Sliding window closes the fixed-window boundary burst hole** — the cap holds
  at every instant, not just at bucket boundaries.
- **Redis semantics = atomic, data-driven, self-trimming:** one Lua script
  (`ZREMRANGEBYSCORE → ZCARD → ZADD`) executes the check-and-add without
  interleaving, computes windows from stored timestamps, and bounds ZSET size by
  the limit.
- **Per-key independence** (per-client locks, sharding by key hash) is what makes
  the limiter scale; one hot client can't serialize the fleet.
- **Memory is `clients × limit`** — the deployment trigger for the O(1)
  approximation; latency is one round trip — the trigger for local pre-filtering.
- **Fail-open is a policy, not a default.** Choose per tier, measure with
  `overAdmission`, and never let the limiter own availability.
