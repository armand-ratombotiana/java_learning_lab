# Mock Interview: Payment System Design

> System Design Mock Interview — 45-minute session

---

## Setup

**Role**: Payments Engineer Interviewer  
**Candidate Level**: Senior Staff Engineer (L6)  
**Problem**: Design a payment processing system for a global e-commerce platform.

---

## Transcript

**Interviewer**: "Design a payment system that processes $10B/month across 50+ countries, 200+ payment methods, and 50 currencies. Key requirements: 99.999% uptime, no double charges, full audit trail."

**Candidate**: "Payment systems are the most critically important systems in tech — money and trust are on the line. I'll design for correctness first, then performance."

**Interviewer**: "Start with the high-level architecture."

**Candidate**: "Layers: 1) API Gateway — validates requests, handles idempotency, rate limits. 2) Payment Service — orchestrates the payment workflow as a state machine. 3) Payment Processor Adapters — abstraction layer over different PSPs (Stripe, Adyen, PayPal). 4) Ledger Service — double-entry bookkeeping. 5) Reconciliation Service — matches internal records with bank statements. 6) Fraud Detection — real-time risk scoring."

**Interviewer**: "How do you prevent double charges?"

**Candidate**: "Idempotency is the key. Every charge request carries an idempotency key (UUID generated by the client). The Payment Service stores the key → response mapping. If it sees the same key within the retention window (7 days), it returns the stored response without processing again. The idempotency store is a replicated database with strong consistency."

**Interviewer**: "Walk me through the payment state machine."

**Candidate**: "States: initiated → authorization → authorized → capture → captured → settlement → settled. Or failure paths: authorization_failed, capture_failed, refunded, partially_refunded, chargeback. Each state transition is recorded as an immutable event in the Ledger Service. The state machine ensures that transitions are valid — you can't capture before authorization."

**Interviewer**: "How does the Ledger Service work?"

**Candidate**: "Double-entry bookkeeping. Every financial event creates two entries: a credit to one account and a debit to another. Example: $10 purchase → credit $10 to merchant account, debit $10 from customer account. The sum of all credits equals the sum of all debits at all times. The Ledger stores transactions in an append-only format — no updates, only inserts."

**Interviewer**: "How do you handle settlement and reconciliation?"

**Candidate**: "Settlement: After capture, the system schedules settlement with the payment processor. The processor sends funds to the merchant's bank account (usually T+1 or T+2). Reconciliation: daily job that compares our ledger entries with the settlement reports from the bank. Each matched transaction is marked 'reconciled'. Unmatched entries trigger investigation."

**Interviewer**: "How do you handle payment processor failures?"

**Candidate**: "Circuit breaker per processor. If a processor returns errors (timeouts, 5xx), we track the error rate. After N consecutive errors (or Y% in a window), the circuit opens. Subsequent requests try the next processor in the priority list. Background health check probes the failed processor. When it recovers, the circuit closes. This also handles failover — if Adyen is down, route through Stripe."

**Interviewer**: "How about testing such a critical system?"

**Candidate**: "Multiple testing layers: 1) Unit tests for business logic (state machine, idempotency). 2) Integration tests with test payment processor sandboxes. 3) Chaos engineering — randomly fail payment processor connections, simulate network partitions. 4) Replay tests — capture production traffic and replay through new system versions. 5) Audit verification — programmatically verify that at any point, the ledger balances."

---

## Key Takeaways

- **Idempotency**: The foundation of safe payment processing
- **State machine**: Enforces valid payment lifecycle transitions
- **Double-entry ledger**: Every credit has a corresponding debit
- **Circuit breaker per processor**: Automatic failover between payment gateways
- **Reconciliation**: Daily matching of internal records with bank statements
- **Comprehensive testing**: Chaos, replay, audit verification for correctness
