# Mock Interview — SIEM & Security Monitoring

## Interviewer: Detection & Response Engineer (45 min)

**Q1: Design a log management pipeline for a global enterprise with 20,000 employees and hybrid cloud infrastructure.**

Candidate: Log sources — endpoints (Windows Event Log: 4688 process creation, 4624/4625 login events; syslog from Linux servers), cloud audit logs (AWS CloudTrail — management events + data events for S3; AWS Config — resource changes; GuardDuty — threat detections; Azure Activity Log; GCP Audit Logs), network (VPC Flow Logs, DNS query logs, firewall logs), identity (Active Directory logs, OAuth audit logs, VPN logs), application (REST API access logs, authentication logs, error logs from all microservices), EDR (CrowdStrike or Defender alerts). Collection — deploy log shippers on each source: Filebeat for servers, AWS FireLens for ECS/Fargate containers, fluentd via DaemonSet in Kubernetes. Use Cribl Stream for routing, filtering, and transformation at edge. Centralized buffer — Kafka cluster (partitioned by log type, replicated across availability zones) to handle ingestion spikes. Normalization — convert all logs to Elastic Common Schema (ECS) — standard field names (source.ip, event.action, user.name, etc.). Enrich: geo-IP from source IP, asset context (which business unit, environment, owner), user identity enrichment (manager, department from HR system). Storage tiers — Hot tier (Elasticsearch, SSD-backed, 7 days retention) for real-time search and alerting. Warm tier (Elasticsearch, HDD, 30 days) for investigations. Cold tier (S3/ADLS, Parquet format, 1 year+) for compliance and historical analysis. Capacity planning — target ~10 TB/day for 20K employees. Partition Kafka by source type (cloud, endpoint, network). Elasticsearch cluster: 10 data nodes with 500GB SSD each for hot tier.

**Q2: What is a correlation rule and how do you write effective ones? Give an example.**

Candidate: A correlation rule combines events across different sources or time windows to detect attack patterns that a single event wouldn't reveal. Example — detect password spraying attack: condition: more than 50 failed logins (Event ID 4625) across different usernames from the same source IP within 5 minutes; AND no successful login from that IP in the last 24 hours. Write in KQL (Kusto) or Sigma (cross-platform format):
```
let failedLogins = SecurityEvent
    | where EventID == 4625 and TimeGenerated > ago(5m)
    | where AccountType == "User"
    | summarize dcount(Account) by IpAddress
    | where dcount_Account > 50;
let successfulLogins = SecurityEvent
    | where EventID == 4624 and TimeGenerated > ago(24h);
failedLogins | join kind=leftanti successfulLogins on IpAddress
```
Effective rules: (1) Start with a baseline — understand normal event volumes to set appropriate thresholds. (2) Use sliding windows (not fixed) to avoid boundary misses. (3) Filter out known-good sources (VPN concentrators, vulnerability scanners). (4) Set appropriate severity — not everything is critical. (5) Test with historical data to measure false positive rate before enabling. (6) Include suppression rules — if the same alert fires 100 times for the same host, suppress after the first.

**Q3: How do you minimize false positives in detection rules? Walk through your tuning process.**

Candidate: Phase 1 — Baseline collection: deploy the rule in monitoring-only mode (log matches but no alert) for 2-4 weeks. Collect all matches and categorize them: True Positive (actual attack), False Positive (benign activity that matches the pattern), or Benign True (malicious activity with low impact). Phase 2 — Analyze: for each false positive trigger, identify the pattern: is it a legitimate admin action? A monitoring tool? A known application behavior? Phase 3 — Tune: add exception filters (exclude specific accounts, IP ranges, processes). Adjust thresholds (increase the count window or decrease the time window). Change match logic (require multiple signal types instead of a single pattern). Phase 4 — Enable: deploy in alert-only mode to a subset of environments (dev → staging → production). Monitor alert volume for first 2 weeks. Phase 5 — Review: quarterly review of all rules: remove obsolete rules (deprecated techniques), update thresholds (traffic grows, baselines shift), fold false positive exceptions into permanent filters.

**Q4: Design a SOC dashboard for triaging security alerts.**

Candidate: Dashboard layout: Panel 1 — Alert volume by severity (critical, high, medium, low) as stacked area chart over 24h. Alert on spike >2x baseline. Panel 2 — Top 10 most triggered rules (helps identify noisy rules or brute force campaigns). Panel 3 — Open incidents by age (time since first alert): <15 min, 15-60 min, 1-4h, >4h. SLO: 100% triaged within 15 min. Panel 4 — MITRE ATT&CK coverage heatmap: x-axis: tactics (Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Exfiltration, Command and Control). y-axis: technique ID. Color: Green (detection exists, alerting), Yellow (detection exists, monitoring only), Red (no detection). Panel 5 — Source IP heatmap: top 10 source IPs triggering alerts. Panel 6 — MTTD/MTTR metrics: 30-day rolling average time to detect and time to respond. Trend comparison (current month vs previous). Panel 7 — Alert assignment: open alerts per SOC analyst, time to assignment. Panel 8 — Recent high-severity alerts with: timestamp, rule name, host/user, current status (open, investigating, contained, resolved). Refresh rate: near-real-time (1-5 seconds) for alerts, 5 min for trends.

**Q5: How do you detect data exfiltration via DNS tunneling?**

Candidate: DNS tunneling encodes stolen data in DNS queries — the attacker establishes a C2 channel using DNS protocol (often allowed through firewalls). Detection methods: (1) Volume anomaly — monitor DNS query volume per host. Baseline: a typical workstation makes 100-500 DNS queries per hour. An infected host making 10,000+ queries/hour is anomalous. Alert on >3x standard deviation from baseline. (2) Domain entropy — DNS tunneling uses high-entropy subdomains to encode data (random-looking strings like "a3k9d8f2h6s1.evil.com"). Measure character frequency distribution — normal queries have human-readable subdomains (api, mail, www). High entropy >3.5 bits/char is suspicious. (3) Rare record types — DNS tunneling often uses TXT records (largest payload capacity) or NULL records. Normal web traffic uses A, AAAA, CNAME, MX records. Alert on TXT queries to non-mail servers. (4) Length analysis — average DNS query length for normal traffic is 20-50 characters. DNS tunneling queries can be 200+ characters. Alert on queries >100 characters. (5) Known domains — compare queried domains against threat intelligence feeds (known tunneling infrastructure, DGAs). (6) Time-based — tunneling maintains persistent connections with regular intervals. Normal DNS has irregular timing.
