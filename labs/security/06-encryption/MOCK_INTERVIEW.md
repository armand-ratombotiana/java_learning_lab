# Mock Interview — Encryption & Cryptography

## Interviewer: Cryptography Engineer (45 min)

**Q1: Compare symmetric vs asymmetric encryption — use cases for each.**

Candidate: Symmetric encryption uses a single shared key for both encryption and decryption. Algorithms: AES-256-GCM (preferred), ChaCha20-Poly1305, and for legacy, AES-256-CBC. Symmetric is extremely fast — modern CPUs have hardware acceleration (AES-NI instructions) enabling gigabytes-per-second throughput. Key distribution is the challenge — how do you securely share the key between parties? Use cases: encrypting data at rest (database encryption, file encryption), TLS session encryption (after the handshake exchanges a session key), and large volume encryption. Asymmetric encryption uses a public/private key pair. Algorithms: RSA (2048-4096 bits), ECDSA (P-256, P-384), and Ed25519. Asymmetric is 1000x slower than symmetric and limited to small payloads (RSA can encrypt up to key size minus padding overhead). Use cases: key exchange (TLS handshake uses ECDHE to establish a shared secret), digital signatures (signing JWTs, code signing, certificate signing), and encrypting small data (wrapping symmetric keys for envelope encryption). In practice, systems use hybrid encryption: asymmetric to establish or exchange a symmetric key, then symmetric for bulk data. TLS does this — ECDHE key exchange establishes a session key, then AES-GCM encrypts the traffic.

**Q2: Why is AES-GCM recommended over AES-CBC in modern systems?**

Candidate: AES-GCM (Galois/Counter Mode) provides authenticated encryption (AEAD) — it combines confidentiality (encryption) with integrity and authenticity (authentication tag) in a single operation. AES-CBC (Cipher Block Chaining) provides confidentiality only — you must separately compute an HMAC to ensure ciphertext hasn't been tampered with. GCM uses CTR mode for encryption (no padding needed, stream-like), and GMAC for authentication. CBC requires padding (PKCS#7), and padding oracle attacks exploit padding validation to decrypt data without the key. GCM is parallelizable — encryption and decryption can use multiple cores. CBC is sequential — each block depends on the previous. GCM's authentication tag is validated before returning plaintext (decrypt-then-verify), detecting tampering. The NIST recommendation is to use GCM for new systems. However, GCM has a limitation: the same nonce must never be reused with the same key (nonce misuse is catastrophic). ChaCha20-Poly1305 is a strong alternative that is more forgiving of nonce misuse and performs better on CPUs without AES-NI.

**Q3: How do digital signatures work and what guarantees do they provide?**

Candidate: A digital signature provides authenticity, integrity, and non-repudiation. The signer: (1) hashes the message with a cryptographic hash function (SHA-256). (2) Encrypts the hash with their private key using an asymmetric algorithm (RSA or ECDSA). The result is the signature. The verifier: (1) hashes the received message with the same hash function. (2) Decrypts the signature with the signer's public key to recover the original hash. (3) Compares the two hashes. If they match, the signature is valid. Authenticity guarantee: since only the private key holder could have produced the signature, the message is authenticated as coming from that entity. Integrity guarantee: if the message was modified in transit, the hashes won't match. Non-repudiation guarantee: the signer cannot credibly deny signing the message (assuming their private key hasn't been compromised). This is legally important for contracts and transactions. In practice: code signing, document signing (PDF signatures), JWT signing, certificate signing (CA signing server certificates), and blockchain transactions. Always sign-then-encrypt (hash then sign the hash), never encrypt-then-sign.

**Q4: Design a key rotation strategy for a system with 500 microservices using envelope encryption.**

Candidate: Envelope encryption architecture: each service gets a Data Encryption Key (DEK) used to encrypt/decrypt its data at rest. The DEK is wrapped (encrypted) by a Key Encryption Key (KEK) stored in a centralized KMS (AWS KMS, Azure Key Vault, or Vault). Only the KEK is stored in the KMS — DEKs are stored alongside the data they encrypt. Two rotation strategies: KEK rotation (simpler) — generate a new KEK version in the KMS, re-wrap all DEKs with the new KEK version. Tag each wrapped DEK with the KEK version used. No data re-encryption needed; only the wrapping key changed. DEK rotation (more secure) — generate a new DEK, re-encrypt all data with the new DEK. Required for compliance if data needs to be re-encrypted periodically. Implementation: use key version identifiers in the metadata stored with encrypted data. On decrypt: read the key version, identify which DEK version encrypted this data, and use the corresponding KEK version to unwrap it. On rotation: for KEK rotation, a background job reads all DEKs, unwraps with old KEK, re-wraps with new KEK. For DEK rotation, re-encrypt active data during low-traffic periods. Automate KEK rotation annually via KMS scheduled rotation. DEK rotation based on data classification (quarterly for PII, annually for other). For 500 services, this needs to be fully automated — a platform team builds the tooling once, all teams adopt it.

**Q5: Explain perfect forward secrecy (PFS) in TLS and how it works.**

Candidate: PFS ensures that a compromise of the server's long-term private key does NOT compromise past TLS session keys. Without PFS (TLS 1.2 with RSA key exchange): the client generates a random pre-master secret, encrypts it with the server's public key (from the certificate), and sends it to the server. Both sides derive the session key from this secret. If an attacker records all traffic and later obtains the server's private key, they can decrypt the pre-master secret and derive all session keys — decrypting ALL past sessions. With PFS (DHE or ECDHE key exchange): both client and server generate ephemeral Diffie-Hellman key pairs for each session. The long-term private key is used only to SIGN the ephemeral DH parameters (authenticating the exchange). The session key is derived from the ephemeral DH keys, which are discarded after the session ends. Even with the server's long-term private key, an attacker cannot derive the ephemeral keys because they were discarded. The attacker would need to solve the Diffie-Hellman problem (discrete log) for each session individually — computationally infeasible. TLS 1.3 mandates PFS for all cipher suites — no option for non-PFS key exchange. For TLS 1.2, prefer ECDHE-RSA ciphersuites. ECDHE (using elliptic curves) is more efficient than DHE (using modular exponentiation).
