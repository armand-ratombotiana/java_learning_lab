# Mock Interview — API Security Testing

## Interviewer: Lead Application Security Engineer (45 min)

**Q1: Walk me through your methodology for pentesting a REST API — from reconnaissance to exploitation.**

Candidate: Phase 1 — Reconnaissance: discover all endpoints from OpenAPI/Swagger docs (if available), URL patterns, and naming conventions. Use directory brute-forcing (ffuf, gobuster) to find hidden endpoints. Check Wayback Machine for historical endpoints. Read mobile app traffic (mitmproxy) to find endpoints not documented publicly. Identify authentication method (JWT, session cookie, API key, OAuth). Phase 2 — Authentication: test for weak password policies, no rate limiting (brute force), JWT algorithm confusion (test alg:none, RS256→HS256), token expiration bypass, insecure cookie flags, session fixation. Phase 3 — Authorization: test IDOR by changing IDs in URLs, request bodies, and query parameters (horizontal — try other users' data, vertical — access admin functions as regular user). Test for forced browsing (access admin endpoints directly). Phase 4 — Injection: SQLi by injecting in query parameters (`?id=1' OR '1'='1`), NoSQLi by manipulating JSON operators (`{"$gt": ""}`), command injection in filenames or headers, template injection (SSTI) in parameters reflected in responses. Phase 5 — Input validation: XSS in response bodies, SSRF by providing internal URLs (`http://169.254.169.254/` for cloud metadata), XXE (if server parses XML), mass assignment (adding unexpected fields in JSON requests). Phase 6 — Business logic: parameter tampering (changing quantities, prices, states), integer overflow, race conditions (concurrent endpoint calls), workflow skipping (bypassing steps). Phase 7 — Configuration: review CORS headers, security headers (HSTS, CSP, X-Frame-Options), TLS version/ciphers, error messages (information disclosure in stack traces), HTTP methods (can you PUT to a read-only endpoint?).

**Q2: What tools do you use for API security testing and how do you integrate them into CI/CD?**

Candidate: Burp Suite Professional for manual testing — intercept traffic, modify requests, replay (Repeater), automate attacks (Intruder), and scan for common vulnerabilities (Scanner). OWASP ZAP for automated CI/CD scanning — run a baseline or full scan against the staging environment. Custom scripts using Python requests library for complex, multi-step business logic tests. jwt_tool for JWT-specific testing (alg confusion, key brute force, claim manipulation). SQLMap for automated SQL injection detection and exploitation (carefully, with target approval). nuclei for template-based vulnerability scanning — use pre-built API security templates or write custom ones. ffuf for endpoint discovery and fuzzing parameters. In CI/CD pipeline: (1) Build time — SAST (semgrep, CodeQL) checks for insecure patterns in API code. (2) Deploy to staging — OWASP ZAP automated scanning against staging URLs, generates report, fails build on critical findings. (3) Pre-production — manual penetration testing with Burp Suite for high-risk changes. (4) Post-deployment — continuous scanning of production with read-only security checks (headers, TLS, CORS), alerting on configuration drift.

**Q3: How does rate limiting work and what common bypass techniques exist?**

Candidate: Rate limiting restricts the number of requests within a time window. Types: (1) Fixed window — count requests per minute, reset at the end of each minute. Simple but allows burst at boundary. (2) Sliding window — moving time window (e.g., last 60 seconds). More accurate, more complex to implement. (3) Token bucket — allows bursts up to capacity, then refills at a steady rate. Good for APIs. (4) Cell-based (sliding window counter) — hybrid approach used by most cloud WAFs. Bypass techniques: (1) Rotate through multiple IPs — if limit is per-IP, use a botnet or proxy rotation. (2) IP spoofing via headers — if the limit uses X-Forwarded-For without validation, inject fake IPs. (3) Distributed attack — each IP sends below the limit, aggregate is large. (4) Timing — if the limit resets at fixed intervals, send bursts just after reset. (5) Low-and-slow — spread requests over long periods. (6) Resource-intensive endpoints — targeting expensive endpoints instead of login. Defense: combine per-IP AND per-user limits, use CAPTCHA after threshold, implement progressive delays (increase delay with each block), use behavioral analysis to detect distributed attacks, log all rate limit triggers for analysis.

**Q4: Design a comprehensive API security testing strategy for a microservices platform.**

Candidate: Four-layer testing: (1) Unit tests — require tests for input validation on every public method. Use parameterized tests to test XSS, SQLi, path traversal patterns. Test authorization logic (ownership checks, role checks). Use OWASP Application Security Verification Standard (ASVS) to guide test coverage. (2) Integration tests — test cross-service flows with security scenarios: user A tries to access user B's data, unauthenticated user hits protected endpoints, expired token rejected, invalid scope rejected. (3) Contract tests — using Pact or Spring Cloud Contract, verify that API providers enforce security constraints documented in the contract (scopes, authentication required). (4) Automated security scanning — SAST (Semgrep, CodeQL) on every PR. Dependency scanning (OWASP Dependency-Check, Snyk) on every build. Container scanning (Trivy) on every image. Secrets scanning (git-secrets, truffleHog) on every commit. DAST (ZAP) on deploy to staging. The pipeline should fail on: any critical/high SAST finding, dependency with publicly known exploit, secret detected in code, container with critical CVE.

**Q5: Describe a real API security vulnerability you discovered and how you handled the disclosure.**

Candidate: Example — discovered a mass assignment vulnerability in a user profile update endpoint at a fintech. The PUT /api/users/{id} endpoint accepted a JSON body that directly set any field on the user object via Jackson deserialization. By adding "role": "ADMIN" to the request body, a regular user could escalate themselves to admin. The fix was a DTO that only allowed specific fields to be updated (whitelist approach). Disclosure: I identified the issue during a scheduled penetration test. I documented the finding with: endpoint details, request/response examples, impact analysis (account takeover, data access escalation), and a specific fix with code example. Reported through the security team's ticketing system. Priority: Critical (CVSS 8.7). Resolution: DTO-implemented and deployed within 12 hours. Post-fix: verified the vulnerability was closed, wrote regression tests, and updated the security checklist for all update endpoints to use whitelist-based field validation.
