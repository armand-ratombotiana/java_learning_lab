# Mock Interview — Security Fundamentals & Authentication Basics

## Interviewer: Senior Security Engineer (40 min)

**Q1: Walk me through the difference between authentication and authorization. Give a concrete example.**

Candidate: Authentication verifies *who you are* — identity verification. Authorization verifies *what you're allowed to do* — permission enforcement. Example: When you badge into an office building, the badge scan authenticates you against the directory. Whether you have access to the server room on the 3rd floor is authorization — the system checks if your badge has that clearance level. In web apps: logging in with username/password is authN; accessing /admin/dashboard is authZ. The key distinction is that authN happens first (establish identity), then authZ happens on every subsequent action (verify permission). Authentication without authorization is useless — you know who the user is but can't control what they do. Authorization without authentication is impossible — you can't grant permissions to an unknown entity.

**Q2: How would you design a password storage system for a new application?**

Candidate: I would use Argon2id with these parameters: unique 16-byte CSPRNG salt per password, memory cost of 64MB, iteration count calibrated so verification takes ~100ms on the production hardware. The stored record includes: algorithm identifier (for future migration), salt (Base64), hash (Base64), and version number. On verification: look up the user, extract the algorithm, salt, and hash, hash the input password with the same salt and parameters, then constant-time compare via MessageDigest.isEqual(). Never log passwords, never send passwords in URLs, never store plaintext even temporarily. Rate-limit verification to 5 attempts per minute per account. For migration: when a user logs in with an old hash, re-hash with Argon2id and update the record. This allows gradual algorithm upgrades without bulk re-hashing.

**Q3: What's the difference between hashing and encryption? When would you use each?**

Candidate: Hashing is a one-way function — given an input, you get a fixed-size output, but you cannot reverse the output to get the input. Encryption is two-way — with the correct key, you can decrypt ciphertext back to plaintext. Hashing is used for: password storage (even if the DB is leaked, attackers can't recover passwords), data integrity checks (file downloads with SHA-256 hash), and data deduplication. Encryption is used for: confidentiality of data at rest (encrypting database fields containing PII), confidentiality of data in transit (TLS), and secure communication (end-to-end encrypted messaging). A common mistake is using encryption where hashing is needed — for example, encrypting passwords instead of hashing them. If the encryption key is compromised, all passwords are recoverable.

**Q4: How do you implement secure session management?**

Candidate: Session ID generation — use SecureRandom to generate at least 32 bytes (256 bits of entropy), Base64URL-encoded. Never use predictable sources like sequential IDs or timestamps. Cookie configuration — set HttpOnly (prevents JavaScript access), Secure (only sent over HTTPS), SameSite=Strict (prevents CSRF), Path=/, and set a reasonable Max-Age. Server-side storage — store session data in Redis with TTL (30 min idle timeout, 8 hour absolute timeout). Session lifecycle — create on login, regenerate on privilege escalation (prevents session fixation), destroy on logout and on password change. Validation — on every request, validate session exists in store, check expiry, check IP and User-Agent for anomaly detection. Revocation — support immediate session invalidation for all sessions or specific sessions. Implement session mgmt UI for users to view and revoke active sessions.

**Q5: You discover that your team's login endpoint has no rate limiting. It's been in production for 6 months. What do you do?**

Candidate: Immediate actions — add temporary rate limiting via the reverse proxy or WAF (5 requests/min per IP). This can be deployed in minutes without code changes. Short-term — add application-level rate limiting incorporating both IP and username-based limits. Account lockout after 10 failed attempts (with CAPTCHA to prevent automated unlock). Medium-term — analyze logs for the past 6 months to check if credential stuffing or brute force attacks occurred. Check for unusual login patterns, high failure rates from specific IPs, or successful logins after many failures. Long-term — implement adaptive rate limiting based on risk factors (new device, unusual location, Tor exit node). Add WebAuthn/FIDO2 for phishing-resistant auth. Implement account alerting on login from new devices. Post-mortem — document the gap, determine why it wasn't caught in code review, add rate limiting to the security checklist for all auth endpoints.
