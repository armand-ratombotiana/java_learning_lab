# Mock Interview — Keycloak Identity & Access Management

## Interviewer: Security Architect (45 min)

**Q1: Explain the Keycloak architecture — realms, clients, users, roles.**

Candidate: Keycloak organizes everything into realms — an isolated tenant representing a security domain. Think of a realm as a complete identity space: one realm for internal employees, another for external customers. Within a realm: Clients represent applications/services that use Keycloak for authentication. Each client can use OAuth 2.0, OIDC, or SAML. Clients have configurations: redirect URIs, client authentication (secret or JWT), and service accounts. Users are the identities — they can log in, have attributes, and belong to groups. Users can be stored in Keycloak's database or federated from LDAP/Active Directory. Roles define permissions. Realm roles are global within the realm; client roles are scoped to a specific client. Composite roles can include other roles (role hierarchy). Groups are sets of users with shared role mappings — assign roles to a group, all members inherit them. Authentication flows define how users authenticate — browser SSO, direct grant (username/password), or Kerberos. Each flow can have required, alternative, or conditional execution steps.

**Q2: How does Keycloak integrate with a Spring Boot application?**

Candidate: Modern approach (Spring Security 6+): Configure Spring as an OAuth 2.0 resource server pointing to Keycloak. In application.yml: spring.security.oauth2.resourceserver.jwt.issuer-uri: https://keycloak.example.com/realms/myrealm. Spring auto-configures JWK set retrieval from the issuer's .well-known/openid-configuration. For the client side (login): use Spring Security's OAuth 2.0 client support with Keycloak as the provider. Configure client-id, client-secret, and scopes in application.yml. For Java config: extend from OAuth2ResourceServerConfigurer. The JwtDecoder is auto-configured when the issuer-uri is set. For custom claims mapping (realm roles to Spring authorities), implement a custom GrantedAuthoritiesMapper that extracts roles from the JWT's realm_access.roles claim. For complete control use a custom JwtAuthenticationConverter. Keycloak-specific: the issuer URL includes the realm name. Each realm has its own JWKS endpoint.

**Q3: How would you set up SAML federation with Keycloak?**

Candidate: Create a new client in Keycloak with SAML protocol. Configure: (1) Client SAML Entity ID — the unique identifier for the SP (same as the SP's entity ID). (2) SAML Assertion Consumer URL — the SP's endpoint that receives the SAML response. (3) Signature keys — generate or import an RSA key pair for signing SAML requests (optional, for signed authn requests). (4) Name ID format — typically email or persistent. (5) Attribute mapping — configure which user attributes (email, firstName, lastName, groups) to include in the SAML assertion. Export the IdP metadata from Keycloak's /realms/{realm}/protocol/saml/descriptor endpoint — this XML contains the SSO URL, SLO URL, and signing certificate. Import this into the SP. For SP-initiated SSO: the SP redirects to Keycloak's SAML endpoint (client_saml_endpoint) with an AuthnRequest. Keycloak authenticates the user and POSTs a signed SAML response back to the ACS URL. The SP validates the response signature and processes the assertion.

**Q4: What are Keycloak authentication flows and when do you use each?**

Candidate: Browser SSO (standard OIDC authorization code flow): User logs in via browser redirect. Supports social login, MFA, passwordless. Used for all web applications where user interaction is expected. Direct Grant (resource owner password credentials): User sends username/password directly to the token endpoint. DEPRECATED in OAuth 2.1. Use only for legacy compatibility or testing. NOT recommended for production — the client sees the user's password. Client Credentials: Machine-to-machine authentication. No user involvement. Used for backend services and APIs calling each other. Kerberos/SPNEGO: Windows-integrated authentication. Used in enterprise environments with Active Directory. User is automatically authenticated based on their Windows domain login. MFA flows: TOTP (Google Authenticator), WebAuthn (biometric or security key), OTP via email/SMS, or backup codes. Conditional authentication: Use authentication flows with conditions — only require MFA if the user is accessing from an untrusted network, a new device, or accessing a high-value application. Execution requirements: required (must pass), alternative (choose one), or conditional (evaluate before executing).

**Q5: Design a high-availability Keycloak deployment for a global enterprise.**

Candidate: Database — use PostgreSQL with streaming replication (primary in primary region, read replicas in others). Avoid embedded H2 or H2 in production. Nodes — deploy multiple Keycloak nodes behind a regional load balancer (ALB or NLB). Each node is stateless regarding sessions (stored in Infinispan distributed cache). Infinispan — configure a distributed cache for user sessions, offline sessions, and login failures. Use UDP multicast or TCPPING for cluster discovery. Cache replication across regions via Cross-Datacenter Replication (JDBC_PING or custom discovery). TLS — terminate TLS at the load balancer, or configure Keycloak's TLS certificates directly. Monitoring — monitor JVM heap usage (set -Xms and -Xms to equal, 2-4 GB per node), database connection pool size, authentication rate, and error rates. Export metrics via Micrometer to Prometheus/Grafana. Backups — full database backup daily, realm export (keycloak export) weekly, store offline. Disaster recovery — second region with passive Keycloak nodes. Promote to active if primary fails. Database cross-region replication. DNS failover (Route53 or Global Traffic Manager). Secrets — master admin password in Vault, not in config files. Theme customization — deploy custom themes as JARs or file-based.
