# Mock Interview — Secrets Management

## Interviewer: Infrastructure Security Engineer (45 min)

**Q1: What is a "secret" in the context of secrets management and what makes it different from regular configuration?**

Candidate: A secret is any sensitive credential used by software to authenticate or authorize: database passwords, API keys, TLS private keys, SSH keys, OAuth tokens, encryption keys, service account JSON keys, and session signing keys. The key characteristics that distinguish secrets from configuration: (1) Secrets grant access to resources or data — a leaked DB password means a data breach. (2) Secrets should be machine-identities, not human-identities — they're used by services to authenticate to other services. (3) Secrets need regular rotation — old credentials should expire. (4) Secrets require audit — every access to a secret should be logged. (5) Secrets must be encrypted at rest and in transit. Configuration (port numbers, feature flags, URLs) doesn't have these properties. A core principle: never store secrets in source code, environment variables in deployment configs, or configuration files that end up in version control.

**Q2: Design a secrets management solution for a Kubernetes-based microservices platform using HashiCorp Vault.**

Candidate: Deploy Vault in the Kubernetes cluster using the Helm chart. Use an external storage backend (PostgreSQL or Consul) for data persistence, not Vault's integrated storage file (though integrated storage is acceptable for smaller clusters). Auto-unseal: wrap the master key with a KMS key (AWS KMS, Azure Key Vault, or Google Cloud KMS) — on Vault startup, it uses the KMS to decrypt the master key, avoiding manual unseal. Authentication: use the Kubernetes auth method — each pod authenticates using its service account token. Vault validates the JWT with the Kubernetes API server token review endpoint. Authorization: define Vault policies per application. Policy "app-db" grants: path "database/creds/app-role" { capabilities = ["read"] } — the app's pod can only read its own database credentials. Secrets injection: use Vault Agent Injector (mutating webhook) — adds a Vault Agent sidecar container to each pod. The sidecar authenticates, fetches secrets, writes them to a shared memory volume (emptyDir, mounted at /vault/secrets), and handles renewal. Application code reads secrets from files — no direct Vault API calls needed. Dynamic secrets: use Vault's Database Secrets Engine to generate short-lived PostgreSQL/MongoDB credentials on-demand (TTL: 15 min-1 hour). No more static DB passwords in config maps.

**Q3: How do you handle database credentials across multiple environments?**

Candidate: Never share secrets between environments. Dev, staging, and prod each have their own Vault instance or separate paths within a single Vault (with separate policies). Dev Vault uses ephemeral databases (auto-provisioned, no sensitive data). Staging uses clones of production schema with sanitized data. Production uses the production databases. Each application instance authenticates to Vault and requests credentials scoped to its environment. Rotation: dynamic DB credentials auto-expire after TTL. For legacy databases that can't use dynamic secrets: implement password rotation via a cron job or Vault rotation plugin. Store a versioned secret in Vault's KV store and rotate on schedule. Applications detect credential changes via Vault Agent's template generation with file change notification.

**Q4: What's the difference between static, dynamic, and ephemeral secrets and when would you use each?**

Candidate: Static secrets are long-lived credentials stored in the secrets manager. Examples: legacy API keys, third-party service credentials, TLS certificates. Pros: simple. Cons: exposure window is long, rotation requires coordination, vulnerable to leaks. Use static secrets only when the target system doesn't support dynamic credential generation. Rotate them regularly. Dynamic secrets are generated on-demand by the secrets platform. Examples: Vault-generated database credentials, AWS STS temporary credentials. They have a TTL (typically hours) and are automatically revoked after expiry. Pros: limited exposure window, no manual rotation, each service gets unique credentials. Use dynamic secrets for all services that support it. Ephemeral secrets are created for a single operation and immediately destroyed. Examples: one-time tokens, response-wrapped secrets in Vault (a secret is wrapped in a single-use token, delivered out-of-band). Use for: zero-trust secret delivery (a human requests a wrapping token, provides it to a server, the server unwraps and gets the secret — the human never sees the actual value), bootstrap secrets, or CI/CD pipeline credentials.

**Q5: How do you audit and monitor secret access to detect compromise?**

Candidate: Enable Vault audit logging to a dedicated file or syslog. Audit logs contain: timestamp, identity (token, user, or service account), path accessed, operation (read, write, list), response (whether access was granted or denied), and request metadata (source IP, user agent, X-Forwarded-For). Forward audit logs to the SIEM (Elasticsearch, Splunk, or Datadog). Create alerts for: (1) Denied access attempts — may indicate a brute force attack on a Vault token. (2) Bulk secret reads — more than 50 secrets read within 5 minutes from a single identity (possible data exfiltration). (3) Access from unusual locations — a service account normally authenticates from cluster IP range, but is now coming from a public IP. (4) Access patterns — a pod that usually reads 1 secret per startup suddenly reads 50 secrets. (5) Secret reads during off-hours — cronjob workloads should align with expected schedules. Monthly review: compare current secret access patterns against baseline, revoke unused service accounts, rotate dormant credentials. Integration: Vault sends audit events to a Kafka topic consumed by the security analytics pipeline for real-time correlation.
