# Mock Interview — WebAuthn & Passkeys

## Interviewer: Authentication Security Engineer (45 min)

**Q1: How does WebAuthn work at a high level? Walk through the registration ceremony.**

Candidate: WebAuthn uses public key cryptography for passwordless authentication. Registration ceremony: (1) Server generates a random challenge (at least 16 bytes) and sends it to the browser along with the Relying Party (RP) info — origin (https://example.com), RP ID (example.com — must be a registrable domain), RP name, and user info (user ID, display name). (2) Browser calls navigators.credentials.create() with these options. (3) The authenticator (platform: Touch ID, Windows Hello, Android biometric, or cross-platform: YubiKey) prompts the user for consent (fingerprint, PIN, presence). (4) Authenticator generates a new key pair — the private key is securely stored in the authenticator's secure hardware (TPM, Secure Enclave). The public key is returned to the browser along with a credential ID, attestation object (proving the authenticator's type), and signature. (5) Browser returns the credential to the server. (6) Server validates the attestation (optional — for enrollment, you may verify the authenticator is genuine), stores the credential ID + public key associated with the user, and confirms registration. The private key NEVER leaves the authenticator — it cannot be copied, exported, or stolen even if the server is compromised.

**Q2: How does WebAuthn prevent phishing where other MFA methods fail?**

Candidate: WebAuthn's phishing resistance comes from origin binding. The key pair is cryptographically bound to the RP ID (the website domain). When the user tries to authenticate, the browser checks that the requesting site's origin matches the RP ID the credential was created for. Example: if a user registers a passkey on webauthn.io, and later visits webauthn-io.evil.com, the browser will NOT offer the credential for the evil site — the RP IDs don't match. This is fundamentally different from passwords (user types their password anywhere) and TOTP (a user can be tricked into entering their 6-digit code on a fake site). Even if an attacker has a convincing phishing page, the browser's WebAuthn implementation will refuse to release the private key because the RP ID check fails. This is also true for passkeys synced via cloud (iCloud Keychain, Google Password Manager) — the origin binding is maintained across devices.

**Q3: Compare platform authenticators vs cross-platform authenticators vs passkeys.**

Candidate: Platform authenticators are built into the device — Touch ID (macOS/iOS), Windows Hello (TPM-based), Android biometric. Pros: convenient (biometric), always available. Cons: not portable — can't log in from another device. Cross-platform authenticators are external hardware — YubiKey, Feitian USB keys, Google Titan. Connected via USB, NFC, or BLE. Pros: portable, can be used across devices, high security (phishing-resistant, hardware-bound). Cons: can be lost, need to manage backup keys. Passkeys bridge this gap — platform authenticators that sync credentials across the user's devices via the platform vendor's cloud. Apple: iCloud Keychain syncs passkeys between iPhone, iPad, Mac. Google: Password Manager syncs across Android and Chrome. The private key is encrypted end-to-end during sync, so the cloud provider cannot access it. Users can use passkeys on any of their own devices but NOT on someone else's device. Best of both worlds: convenient (biometric), synced (across your devices), and phishing-resistant.

**Q4: How do you handle account recovery for passwordless-only users?**

Candidate: Passwordless systems need a carefully designed recovery path because losing your authenticator means losing access. Strategy: (1) Multi-device enrollment — require users to register at least two authenticators during enrollment (phone's biometric + a hardware key or a backup device). (2) Recovery codes — generate 10-16 one-time recovery codes at enrollment. Codes are displayed once and should be stored offline. Each code can be used once for login. After using a code, the user must re-register authenticators. (3) Out-of-band verification — email or SMS code to a verified address/phone. This is weak (phishing-prone) but works as a fallback. (4) Escrow process — if all else fails, an administrator can initiate a recovery flow requiring identity verification (ID document, manager approval). (5) Trusted contacts — user designates trusted contacts who can vouch for their identity (multi-party recovery). (6) Time delays — for high-security applications, add a cooldown period before recovery completes. Best practice: force enrollment of 2 authenticators, show recovery codes, and have a managed escrow process. Log all recovery attempts and alert on suspicious patterns.

**Q5: Design a complete passkey-based authentication system for a web application with mobile support.**

Candidate: Backend — store registered credentials in a table: credential_id (unique, from authenticator), user_id, public_key (DER-encoded), sign_count (for counter-based cloning detection), credential_type (platform/cross-platform), device_name (user-friendly), created_at, last_used_at. Endpoints: POST /auth/register/begin — generates challenge, returns PublicKeyCredentialCreationOptions including RP info, user info, and excludeCredentials (existing credential IDs). POST /auth/register/complete — receives credential object, validates attestation, stores credential. POST /auth/login/begin — generates challenge, returns PublicKeyCredentialRequestOptions with allowCredentials (list of user's credential IDs). POST /auth/login/complete — receives assertion, verifies signature against stored public key, checks sign_count (must be strictly increasing — if not, possible cloning attack). Frontend — registration: const cred = await navigator.credentials.create({publicKey: options}); serializes cred and sends to server. Login: const assertion = await navigator.credentials.get({publicKey: options}); sends to server. Session management — after successful WebAuthn, create a traditional session or issue a JWT. The user does NOT enter a password. For progressive enrollment: allow users with passwords to add a passkey in account settings, then make passkey the primary login method.
