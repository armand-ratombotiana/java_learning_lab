# Mock Interview — JWT (JSON Web Tokens)

## Interviewer: Lead Application Security Engineer (40 min)

**Q1: Describe the structure of a JWT and how it is constructed.**

Candidate: A JWT has three Base64URL-encoded parts separated by dots: header.payload.signature. The header typically contains `{"alg":"RS256","typ":"JWT","kid":"key-id-2024"}` — the algorithm used to sign the token, the token type, and optionally a key ID for key rotation. The payload (claims) contains statements about the entity and metadata: `{"sub":"user_abc123","exp":1700000000,"iat":1699996400,"iss":"https://auth.example.com","aud":"api.example.com","scope":"openid profile email","roles":["admin"]}`. The signature is computed by taking base64url(header) + "." + base64url(payload), then signing it with the specified algorithm using the private key (for RS256) or shared secret (for HS256). All three parts are Base64URL-encoded (uses URL-safe characters, no padding). Anyone can base64-decode the header and payload — JWTs are NOT encrypted by default. They are signed to prevent tampering. For sensitive claims, use JWE (JSON Web Encryption) to encrypt the payload, or don't put sensitive data in the JWT at all.

**Q2: What are the most common JWT attacks and how do you prevent each?**

Candidate: Attack 1 — alg:none attack: The attacker sets the algorithm to "none" and removes the signature. Many older JWT libraries would accept tokens without signature. Prevention: explicitly verify the algorithm is in an allowlist (e.g., must be RS256 or ES256, reject "none"). Attack 2 — Algorithm confusion (asymmetric to symmetric): The attacker changes alg from RS256 to HS256 and signs the token with the server's PUBLIC key (since HS256 uses a symmetric secret, and the public key is... public). The server verifies the token using the public key as the HMAC secret, which matches. Prevention: always validate the algorithm against the key type — if the key is RSA, only allow RS256/RS384/RS512. Attack 3 — Weak/compromised signing key: If HS256 is used with a weak secret, attackers can brute-force it. Prevention: use asymmetric algorithms (RS256, ES256) or strong enough symmetric keys (256-bit random). Attack 4 — Token theft: Attacker intercepts the JWT and replays it. Prevention: short expiry (15 min), TLS for all communication, jti claim for token revocation, token binding to client. Attack 5 — Missing claim validation: The server doesn't verify exp, iss, aud, nbf. Prevention: validate ALL claims server-side. Attack 6 — JWK injection: Some libraries accept a jwk header specifying the verification key. Attacker provides their own public key. Prevention: disable JWK header injection, use configured or JWKS endpoint keys only.

**Q3: Why would you choose RS256 over HS256 for JWTs in a microservice architecture?**

Candidate: RS256 uses asymmetric cryptography — the auth server holds the private key for signing, and all resource servers hold only the public key for verification. With HS256, every service that needs to verify tokens must possess the same shared secret. In a microservice architecture with 50+ services, HS256 means 50+ places where the secret is stored, increasing the attack surface and complicating rotation. If any one service is compromised, the attacker has the secret and can forge tokens for any user. With RS256, even if a resource server is compromised, the attacker gets only the public key, which can't sign new tokens. The compromise is isolated to that service. Additionally, key rotation is simpler with RS256 — you publish new public keys to the JWKS endpoint and old tokens remain valid until they expire. With HS256, rotating the secret invalidates all tokens unless you coordinate timing across all services.

**Q4: How do you handle JWT revocation since JWTs are stateless?**

Candidate: Stateless JWTs are designed to be self-validating without server-side storage, which means immediate revocation is not natively supported. Approaches include: (1) Short expiry — if tokens expire in 15 minutes, the exposure window is small. Combine with refresh tokens that ARE revocable. (2) Token blocklist — maintain a Redis set of revoked jti values. The blocklist endpoint must be called on every request, adding latency. Manage cache TTL to keep the set small. (3) Token version — store a token_version integer in the user's database record. If the user's token_version > the version in the JWT, reject the token. Increment version on password change, logout, or compromise. This doesn't require a blocklist but does require a DB lookup on every request. (4) For high-security scenarios — use opaque tokens with server-side state instead of JWTs. The token is a random string referencing stored session data. Immediate revocation is trivial — delete the session. (5) Hybrid approach — use JWTs for short-lived access (15 min) and server-side refresh tokens (revocable) for session management. Most practical for most applications.

**Q5: Walk through complete JWT validation on a resource server.**

Candidate: Step 1 — Extract the token from the Authorization: Bearer header. Step 2 — Split the token on dots into three parts. Verify there are exactly three parts. Step 3 — Base64URL-decode the header. Parse as JSON. Validate the algorithm is in the approved list (e.g., ["RS256"]). Extract the kid if present. Step 4 — Fetch the signing key. If kid is present, look up the key in the JWKS cache by kid. If no kid, check if we have a single configured key. Validate the key type matches the algorithm (RSA key for RS256). Cache the JWKS and refresh periodically (every hour). Step 5 — Verify the cryptographic signature using the public key. Most libraries handle this with a single method call. Step 6 — Base64URL-decode the payload. Parse as JSON. Step 7 — Validate exp: current time must be before exp (allow 30-second clock skew). Step 8 — Validate nbf if present: current time must be after nbf. Step 9 — Validate iss: must match the expected issuer URL (the auth server). Step 10 — Validate aud: must include this resource server's identifier. Step 11 — Validate other claims as needed: azp (authorized party), scope (required permissions). Step 12 — Check jti against a blocklist if implementing revocation. Step 13 — Extract subject and custom claims for authorization decisions. Step 14 — Create authenticated principal or Authentication object for the request context.
