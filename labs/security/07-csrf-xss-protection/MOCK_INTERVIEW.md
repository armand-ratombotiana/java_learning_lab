# Mock Interview — CSRF & XSS Protection

## Interviewer: Web Security Engineer (40 min)

**Q1: Describe how Cross-Site Scripting (XSS) works and the three types you'd encounter.**

Candidate: XSS injects malicious JavaScript into web pages viewed by other users, bypassing the same-origin policy. Stored XSS — the attacker's payload is permanently stored on the server (e.g., in a database comment field, forum post, or profile bio). Every user who views the page executes the script. Highest impact because it reaches many victims without requiring them to click a crafted link. Reflected XSS — the payload is in the HTTP request itself (URL parameter, form field) and is immediately reflected in the response. The attacker crafts a malicious link and tricks the victim into clicking it. The victim's browser sends the request, the server reflects the payload in the response, and the browser executes it. DOM-based XSS — the vulnerability exists entirely in client-side JavaScript. The server response is safe, but the client-side script reads attacker-controlled input (from URL fragment, window.name, localStorage) and writes it to the DOM unsafely (innerHTML, document.write). The attacker's JavaScript executes in the victim's session context, enabling: cookie theft (if HttpOnly not set), session hijacking, keylogging, defacement, redirection to phishing sites, and actions performed as the victim.

**Q2: How does Content Security Policy (CSP) prevent XSS? Walk through a configuration.**

Candidate: CSP is a browser security mechanism that defines allowed content sources via HTTP headers. The header Content-Security-Policy tells the browser what's allowed and what's blocked — scripts, styles, images, fonts, etc. CSP prevents XSS by blocking inline scripts, eval(), and restricting script sources to trusted origins. Example policy: default-src 'self'; script-src 'self' https://cdn.example.com 'nonce-rAnd0m'; style-src 'self' 'nonce-rAnd0m'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; upgrade-insecure-requests. Key directives: script-src controls JavaScript sources. For inline scripts, use nonces (server generates a random nonce per request, script tag includes nonce="rAnd0m", CSP includes 'nonce-rAnd0m') or hashes. Avoid 'unsafe-inline' — it allows all inline scripts, completely defeating XSS protection. object-src 'none' blocks Flash and plugins. base-uri restricts base tag injection. form-action limits form submission targets. frame-ancestors prevents clickjacking by restricting which sites can frame your page. Implementation: start in report-only mode (Content-Security-Policy-Report-Only) and monitor reports before enforcing. Use report-uri or report-to directives to collect violations. CSP with nonces provides defense in depth — even if a developer accidentally introduces an XSS vulnerability, the browser won't execute the injected script if it lacks the valid nonce.

**Q3: Explain CSRF and how SameSite cookies prevent it.**

Candidate: CSRF (Cross-Site Request Forgery) forces an authenticated user to execute unwanted actions on a web application they're currently logged into. The attacker crafts a form or request that performs a state-changing action (transfer money, change password, delete account). When the victim visits the attacker's page, the browser automatically includes cookies for the target site. Since the request appears to come from the logged-in user, the server processes it. SameSite cookie attribute prevents this: SameSite=Strict — the cookie is NEVER sent on cross-site requests. Best for security but user experience impact (clicking a link from email to a SaaS app shows a logged-out state). SameSite=Lax (the modern browser default) — the cookie IS sent for top-level navigations using safe HTTP methods (GET). Form submissions (POST), iframes, images, and scripts from other sites don't include the cookie. This covers most CSRF scenarios while preserving safe deep-linking. SameSite=None — the cookie is sent on all cross-site requests. Requires Secure flag (HTTPS only). Use only when necessary (e.g., third-party widgets, analytics). Implementing SameSite is a critical defense but not sufficient alone for high-security actions — also require CSRF tokens for sensitive operations (password change, fund transfers, email change).

**Q4: How would you output user-generated content safely in different HTML contexts?**

Candidate: Context-aware escaping is critical — the same encoding doesn't work in all contexts. HTML body context: `<p>${encodeHtml(userInput)}</p>`. Encode: & → &amp;, < → &lt;, > → &gt;, " → &quot;, ' → &#x27;/. Using a template engine with auto-escaping (Thymeleaf with th:text, React with JSX text content) handles this automatically. HTML attribute context: `<a class="${encodeAttr(userClass)}">`. Encode: in addition to HTML entities, escape spaces and quote characters. Never use user input for event handler attributes (onclick, onerror) — even with encoding, they're dangerous. JavaScript context: `<script>var msg = '${encodeJs(msg)}';</script>`. Encode: backslash-escape quotes, backslashes, newlines. Better: don't embed user data in JavaScript strings — use data attributes or a JSON API. URL context: `<a href="${encodeUrl(redirectUrl)}">`. URL-encode and validate the URL scheme (reject javascript:, data:). CSS context: value in CSS property. Escape or avoid entirely. The safest approach: use a well-maintained template engine with context-aware auto-escaping (Thymeleaf, Handlebars, React). Never use dangerouslySetInnerHTML, v-html, or innerHTML with user content. For rich text (WYSIWYG editors), use a library like DOMPurify to sanitize HTML to an allowlist of safe tags (b, i, em, strong, a, p, ul, ol, li, br).

**Q5: Design a secure file upload system end-to-end.**

Candidate: Frontend — validate file type by MIME, check file size before upload, display progress. Use multipart/form-data. Backend validation chain: (1) Check upload is authenticated and authorized (user has permission to upload). Rate limit per user (10 uploads/hour). (2) Validate MIME type by checking magic bytes (first bytes of the file), not just the Content-Type header or file extension. Use libraries like Apache Tika for content detection. (3) Validate file extension against an allowlist (jpg, png, pdf, docx — never accept .exe, .jar, .html, .svg). (4) Validate file size (max 10MB for images, 100MB for documents). (5) Scan with ClamAV or cloud-based malware scanner. (6) Rename file to a UUID with the original extension (prevent path traversal via filenames like ../../../etc/passwd). (7) Store outside web root — use cloud storage (S3, GCS) with private access. Serve files via pre-signed URLs with expiry (60 seconds to 1 hour). (8) Set Content-Disposition: attachment for untrusted types to prevent browser rendering. Set Content-Type to the actual MIME type (not user-supplied). (9) For images, re-encode them (strip EXIF metadata, resize) to remove embedded malware/steganography. (10) For PDFs, sanitize with tools like Dangerzone or PDFSandbox. Logging — log all uploads (user, filename, size, type, timestamp) for audit. Alert on rejected uploads (possible attack probing).
