# Mock Interview — OAuth 2.0 & Authorization Frameworks

## Interviewer: Security Architect (45 min)

**Q1: Explain the OAuth 2.0 authorization code flow step by step.**

Candidate: Step 1 — Client (web app) redirects the user's browser to the authorization server with query parameters: response_type=code, client_id (public identifier), redirect_uri (where to send the code), scope (requested permissions like "openid profile email"), and state (CSRF token). The state parameter is critical — it's a random value the client generates and verifies on callback to prevent CSRF on the auth callback endpoint. Step 2 — The authorization server authenticates the user (login form, possibly MFA) and presents a consent screen showing what permissions the client is requesting. Step 3 — User approves. The auth server redirects the browser to the redirect_uri with a one-time authorization code and the state parameter. Step 4 — The client sends a POST to the token endpoint with: grant_type=authorization_code, code (from step 3), redirect_uri, client_id, and client_secret. Step 5 — The auth server validates the code (single-use, not expired), verifies the client credentials, and returns an access_token (usually a JWT), refresh_token (long-lived, for obtaining new tokens), and optionally an id_token (OIDC). Step 6 — The client stores the tokens (access token in memory, refresh token in HttpOnly cookie) and uses the access token in the Authorization header for API calls. Step 7 — The resource server validates the access token (signature, expiry, audience) on each request before serving data.

**Q2: What is PKCE and when should you use it?**

Candidate: PKCE (Proof Key for Code Exchange, pronounced "pixie") extends the auth code flow to prevent authorization code interception attacks. The client generates a code_verifier (random 43-128 character string using unreserved characters) and sends the SHA-256 hash of it as code_challenge during the initial authorization request with code_challenge_method=S256. When exchanging the code, the client sends the original code_verifier. The auth server hashes the verifier and compares it to the stored challenge. This prevents attacks where an intercepted code cannot be exchanged without the verifier. PKCE was originally designed for mobile and SPA (public clients) that cannot keep a client_secret confidential, but OAuth 2.1 (the updated spec) now requires PKCE for ALL clients, including confidential ones. This is defense in depth — even if your client secret is compromised, the verifier provides additional protection.

**Q3: How do refresh tokens work and what are the security considerations?**

Candidate: Refresh tokens are long-lived credentials issued alongside access tokens. When the access token expires, the client sends the refresh token to the token endpoint to get a new access token without user interaction. Security considerations: (1) Store refresh tokens securely — HttpOnly cookies for web apps, encrypted device storage for mobile. (2) Implement rotation — issue a new refresh token each time one is used, invalidate the old one (prevents replay if token is stolen). (3) Token binding — bind the refresh token to the client_id and device fingerprint. (4) Revocation — support immediate revocation on logout, password change, account compromise, or administrator action. (5) Expiration — set a TTL (7-30 days) with rolling expiration (extend TTL on use). (6) Detection — log all refresh token usage; alert on unusual patterns (new IP, new device, replay attempts). (7) One-time use — if a refresh token is reused (indicates the original was stolen), revoke ALL tokens for that user.

**Q4: Compare OAuth 2.0 client credentials vs authorization code flow.**

Candidate: Client credentials flow is for server-to-server communication with no user involved. The client authenticates directly with its own credentials (client_id + client_secret, or private_key_jwt). No user consent, no redirect, no browser involved. Tokens represent the client application itself, not a user. Ideal for backend services, cron jobs, and API integrations. Authorization code flow involves an end-user. The user authenticates and consents to the client acting on their behalf. Tokens represent a delegated user identity. Use client credentials when your service needs to access its own resources (reading a config service, publishing to a queue). Use authorization code when your service needs to access resources belonging to a user (reading the user's email, accessing the user's files). You can use both in the same application for different operations.

**Q5: Design an OAuth 2.0 authorization server from scratch.**

Candidate: Architecture — expose three endpoints: /authorize (GET), /token (POST), /revoke (POST), and /.well-known/oauth-authorization-server for discovery. The /authorize endpoint handles user authentication (redirect to login page, validate credentials, enforce MFA), generates a one-time authorization code (stored in DB with TTL of 60 seconds and bound to client_id, redirect_uri, and code_challenge), and redirects the user. The /token endpoint validates incoming requests based on grant_type: for authorization_code, verify the code (exists, not expired, not used), verify PKCE if present, authenticate the client (client_secret or private_key_jwt for confidential clients), then generate tokens. Token generation — sign JWTs with RS256 (asymmetric key pair), include claims: iss (issuer URL), sub (user ID), aud (client_id), exp (15 min), iat, jti (unique ID for revocation), and custom claims (roles, scopes). Refresh tokens — opaque strings stored with a hash in the database, bound to user + client, with rotation. Security — rate limiting per client_id and per IP, audit logging on every token/authorization issuance and denial, consent tracking per user per client with revocation capability.
