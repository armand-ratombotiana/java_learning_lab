# Mock Interview — CORS Security Configuration

## Interviewer: Platform Security Engineer (35 min)

**Q1: Explain how CORS works and why it exists.**

Candidate: CORS (Cross-Origin Resource Sharing) is a browser security mechanism that selectively relaxes the Same-Origin Policy. The Same-Origin Policy prevents a web page from origin A from reading responses from origin B — this is fundamental to web security. Without it, any website could make requests to your bank and read the response containing your balance. But sometimes cross-origin access is needed (your SPA at app.example.com needs to call api.example.com or a third-party API). CORS allows servers to declare which origins are permitted. For "simple" requests (GET, HEAD, POST with form content types), the browser adds the Origin header, and if the server responds with Access-Control-Allow-Origin matching that origin, the browser allows the response. For "non-simple" requests (PUT, DELETE, custom headers, application/json), the browser sends a preflight OPTIONS request first. The server must respond with appropriate CORS headers. The browser then makes the actual request. CORS is browser-enforced only — curl or Postman don't enforce CORS. It protects the user's browser session, not the API itself. APIs must still implement proper authentication regardless of CORS.

**Q2: What is the danger of setting Access-Control-Allow-Origin to * on an authenticated API?**

Candidate: ACAO: * tells the browser to allow requests from ANY origin. However, the fetch spec prohibits using ACAO: * with Access-Control-Allow-Credentials: true. If you set credentials=true and ACAO: *, the browser will BLOCK the response (the fetch promise rejects). So with pure ACAO: * and no credentials, the API is essentially public (any site can read the response). This is acceptable for public APIs (weather data, public content) but dangerous for authenticated APIs — even without cookies, if the API uses Authorization headers or API keys, the browser doesn't automatically send them cross-origin, but the attacker could use a proxy to bypass browser restrictions or exploit an SSRF vulnerability. The real danger is with misconfigured servers that echo back the Origin header without validation: Access-Control-Allow-Origin: [Origin header value]. An attacker can make a request from evil.com, and the server echoes Access-Control-Allow-Origin: https://evil.com. Combined with credentials: true, this allows the attacker to make authenticated requests and read responses. Always validate the Origin header against an allowlist, never echo it blindly.

**Q3: How do you handle CORS for APIs using cookies (session-based auth)?**

Candidate: Session auth with cookies requires: Access-Control-Allow-Credentials: true AND Access-Control-Allow-Origin must be a specific origin (not *). The server must: (1) Validate the Origin header against an allowlist. (2) Return the exact origin in ACAO header. (3) Set Vary: Origin for caching. (4) Ensure Set-Cookie includes SameSite=None; Secure (because the request is cross-site). The preflight OPTIONS request must succeed — it's sent without credentials. The preflight response must include ACAO, ACAC: true, and if the server authenticates based on cookies, the OPTIONS handler should not require authentication. This is a common issue — the preflight fails because the server returns 401 for OPTIONS without cookies. Make OPTIONS endpoints public.

**Q4: Design CORS configuration for a multi-tenant API where each tenant has a custom domain.**

Candidate: Each tenant has a domain like tenant1.app.com, tenant2.app.com. The API is at api.app.com. Since origins are dynamic per tenant, a static list won't work. Options: (1) Use a database/Redis lookup — extract the Origin from the request, look up the tenant's configuration, find the allowed origins, and check if the request origin matches. (2) Use regex-based matching — if tenant domains follow a pattern (*.app.com), use allowedOriginPatterns in Spring: config.setAllowedOriginPatterns(List.of("https://*.app.com")). (3) Dynamic origin validation — implement CorsConfigurationSource that checks the Origin against a tenant-specific allowlist stored in a config service. Cache the per-tenant origins for performance. For the preflight response, return the validated Origin. For credentials, set allowCredentials=true. Set Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers for proper CDN caching. Important: even with dynamic origins, validate the Origin is not null (browser always sends Origin for cross-origin requests, but not for same-origin — handle null origin by allowing requests that match the API's own origin).

**Q5: What's the difference between simple and preflight requests?**

Candidate: Simple requests meet ALL these conditions: method is GET, HEAD, or POST; only CORS-safe headers (Accept, Accept-Language, Content-Language, Content-Type) with Content-Type limited to application/x-www-form-urlencoded, multipart/form-data, or text/plain. No event listeners on XMLHttpRequest. No ReadableStream used. Simple requests skip the preflight — the browser directly sends the request with the Origin header. If the response doesn't include ACAO matching the origin, the browser blocks the JS from reading the response but the request IS sent to the server (this is important for CSRF considerations). Preflight requests are triggered by: methods besides GET/HEAD/POST (PUT, DELETE, PATCH), custom request headers (Authorization, X-Requested-With, X-Custom), Content-Type other than the three simple types (including application/json), credentials with XMLHttpRequest. The preflight is an OPTIONS request that asks the server for permission. It includes Access-Control-Request-Method and Access-Control-Request-Headers. The server responds with allowed methods, headers, and origin. If the preflight fails (wrong server response), the browser never sends the actual request. Preflight adds latency (one extra round-trip). Mitigate with Access-Control-Max-Age to cache the preflight response (up to 1 hour). Some modern browsers support "preflight-less" CORS via the `private state token` API for specific use cases.
