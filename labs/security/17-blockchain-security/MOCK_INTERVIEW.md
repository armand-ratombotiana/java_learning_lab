# Mock Interview — Blockchain Security

## Interviewer: Security Researcher (40 min)

**Q1: What are the most common smart contract vulnerabilities and how does each work?**

Candidate: (1) Re-entrancy (DAO hack, 2016 — $60M stolen): a vulnerable contract makes an external call to an untrusted contract before updating its state. The attacker's fallback function calls back into the vulnerable contract, re-entering the withdraw function before the first invocation completes. Mitigation: Checks-Effects-Interactions pattern (update state BEFORE any external call), ReentrancyGuard modifier (OpenZeppelin), limit gas forwarded to external calls. (2) Integer overflow/underflow: arithmetic operations exceed uint256 bounds. Historic example: exchange allowed arbitrary token prices. Mitigation: use Solidity ^0.8.0 (built-in overflow checks) or SafeMath library. (3) Access control flaws: tx.origin used instead of msg.sender (tx.origin is the original signer — a malicious contract can impersonate the user). Missing onlyOwner modifiers on sensitive functions. Mitigation: use msg.sender, use OpenZeppelin's Ownable or AccessControl patterns. (4) Oracle manipulation (bZx hack, 2019): attacker manipulates a price oracle (Uniswap pool price) to liquidate or profit from positions. Mitigation: use TWAP (Time-Weighted Average Price) oracles instead of spot price, use multiple oracle sources, use Chainlink decentralized oracles. (5) Flash loan attacks (numerous DeFi hacks): attacker borrows large uncollateralized loans within one transaction to manipulate prices or exploit protocol logic. Mitigation: TWAP oracles, circuit breakers on large trades, invariant checks, verified randomness.

**Q2: How does a re-entrancy attack work in detail and what are the prevention techniques?**

Candidate: Victim contract: function withdraw(uint amount) public { if (balances[msg.sender] >= amount) { (bool sent, ) = msg.sender.call{value: amount}(""); if (sent) { balances[msg.sender] -= amount; } } } The attacker's contract receives ETH via the call, which triggers the fallback function. The fallback() function calls withdraw() again. Since the balance hasn't been updated yet (the subtraction happens after the send), the attacker can drain all funds. Prevention techniques: (1) Checks-Effects-Interactions: update balances[msg.sender] -= amount BEFORE the external call. (2) ReentrancyGuard: use OpenZeppelin's contract — a modifier that blocks re-entry via a mutex flag. (3) Use transfer() instead of call() for simple ETH sends — transfer() only forwards 2300 gas (enough to log an event, not enough for re-entrancy). But transfer() is now discouraged — use call() with ReentrancyGuard. (4) Pull over Push pattern: users withdraw their funds themselves rather than the contract pushing funds.

**Q3: What is a 51% attack and which blockchains are most vulnerable?**

Candidate: In a proof-of-work (PoW) blockchain, if a single entity controls more than 50% of the network's mining hash rate, they can: (1) Prevent transactions from being confirmed (denial of service). (2) Reverse recently confirmed transactions (double-spending — spend coins, receive goods, then reorganize the block to revert the transaction). They CANNOT: create coins from nothing, modify past transactions (older than the reorganization window), forge signatures. Vulnerability depends on network hashrate distribution. Bitcoin: extremely secure due to massive, decentralized hashrate. Smaller PoW chains (Bitcoin Cash, Litecoin, Ethereum Classic) are more vulnerable — can be rented hash rate from NiceHash to conduct temporary 51% attacks. PoS blockchains (Ethereum 2.0, Solana) use economic security instead — attacking requires owning 33%+ of staked ETH. If validator controls 51%+, they can finalize incorrect blocks but lose their entire stake (slashing) if caught. This makes attacks economically irrational.

**Q4: Walk through your smart contract audit methodology.**

Candidate: Phase 1 — Understand the protocol: read the whitepaper, architecture docs, and codebase. Understand the protocol's invariants (what must always be true). Phase 2 — Automated analysis: run static analysis tools (Slither, Mythril, Aderyn). Slither detects: re-entrancy, unused return values, timestamp dependency, tx.origin usage, incorrect operator precedence. Mythril does symbolic execution to find: assertion violations, integer overflow, re-entrancy. Fuzz testing with Echidna or Foundry's fuzzer to test invariants. Phase 3 — Manual review: read every function in every contract. Check: access control (who can call each function?), input validation (are parameters validated?), state management (are states correctly updated?), external dependencies (oracle model, token interactions, bridge contracts). Phase 4 — Formal verification for critical invariants: use Certora Prover or Scribble to mathematically prove properties like "totalSupply equals sum of all balances" or "user cannot withdraw more than their balance." Phase 5 — Test coverage analysis: ensure tests cover: normal cases, edge cases (zero amounts, max values), attack vectors (re-entrancy, flash loans, oracle manipulation), and upgrade scenarios. Phase 6 — Reporting: document findings with severity (Critical, High, Medium, Low, Gas), provide proof of concept (forge test or hardhat script) for each finding, and recommend fixes.

**Q5: What security considerations exist for blockchain bridges and cross-chain protocols?**

Candidate: Bridges are the most attacked DeFi infrastructure (Ronin $620M, Wormhole $326M, Nomad $190M). Attack vectors: (1) Validator/key compromise — the bridge's trusted validator set is attacked. Ronin: attackers compromised 5 of 9 private keys (4 from Axie DAO validators, 1 from Sky Mavis). Mitigation: higher threshold (7/9), validator diversity (geographic, legal entity), hardware security modules, multi-party computation (MPC). (2) Smart contract bug — the bridge contract has a vulnerability allowing minting of wrapped tokens without proper deposits. Mitigation: formal verification, multiple audits, bug bounty program, restricted upgrade mechanisms (timelock + multisig). (3) Economic manipulation — abusing price differences or liquidity to extract value. Mitigation: rate limits on bridge throughput, on-chain monitoring for anomalous activity, circuit breakers that pause bridging during suspicious conditions. (4) Replay attacks — same message replayed on different chains or directions. Mitigation: nonce tracking per chain, chain ID in messages, expiration timestamps. Best practices: limit total value locked (TVL) in bridges, use multiple independent validators, implement governor-controlled pauses, maintain a reserve fund for incidents, conduct regular security audits.
