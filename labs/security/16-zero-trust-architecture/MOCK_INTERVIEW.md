# Mock Interview — Zero Trust Architecture

## Interviewer: Security Architect (45 min)

**Q1: What are the core principles of Zero Trust? Explain each with an example.**

Candidate: Principle 1 — Verify explicitly: always authenticate and authorize based on ALL available data points, not just network location. Example: a user accessing an internal CRM from the office network must still authenticate with MFA, prove device compliance (OS patched, AV running, disk encrypted), and the request is logged for audit. Principle 2 — Use least privilege: limit access with JIT/JEA (Just-In-Time and Just-Enough-Access). Example: a developer doesn't have standing access to production databases. When an incident requires DB access, they request elevated access through an approval workflow, get a time-limited role (15 minutes), and the role auto-expires. All actions during that window are logged. Principle 3 — Assume breach: design the architecture assuming an attacker is already inside the network. Example: segment workloads so that even if an attacker compromises the web server pod, they cannot automatically reach the database pod without explicit, authenticated authorization (network policy, mTLS). Encrypt all data in transit and at rest. Monitor continuously for anomalous behavior.

**Q2: How does Google's BeyondCorp architecture implement zero trust?**

Candidate: BeyondCorp shifts access control from the network perimeter to individual devices and users. Key components: (1) Access Proxy — all applications are behind an access proxy (similar to Cloudflare Access or IAP on GCP). The proxy evaluates every request against policy before forwarding to the application. There is no VPN required. (2) Identity-Aware Proxy (IAP) — Google Cloud's implementation. Uses user identity (Google Account, G Suite) and context (device information, IP address) to make access decisions. (3) Device Inventory Service — maintains a real-time registry of all corporate devices, their patch status, OS version, disk encryption status, and whether they have a valid certificate. (4) Trust Score — continuous evaluation of device health. If a device falls out of compliance, access is immediately revoked even for established sessions. (5) Policy Engine — evaluates: user identity, device trust score, requested resource sensitivity, and environmental context. Decisions are per-request, not per-session. Implementation: no special client software needed beyond a managed device and standard browser. The access proxy handles all authentication and authorization transparently.

**Q3: What is micro-segmentation and how do you implement it in different environments?**

Candidate: Micro-segmentation creates isolated security zones down to the individual workload level, preventing lateral movement. Traditional network segmentation divides the network into VLANs (one per environment, one per business unit). Micro-segmentation applies policies per workload, regardless of network location. Kubernetes — Network Policies define ingress/egress rules per pod or namespace. Example: frontend pods can talk to backend pods (TCP 8080), backend can talk to database (TCP 5432), but frontend cannot talk directly to database. Cloud — security groups per instance or Auto Scaling group. AWS Security Groups as micro-segmentation: web SG, app SG, data SG. Traffic between groups is explicitly allowed, not implicitly trusted. Virtual networks — SDN solutions (VMware NSX, Cisco ACI, Cilium in Kubernetes) provide host-based firewalling between any workloads. Benefits: if an attacker compromises a web server, micro-segmentation prevents them from reaching the database or other environment tiers.

**Q4: Design a zero trust architecture for a global company with 20,000 employees, hybrid cloud, and remote workforce.**

Candidate: Identity layer — SSO via Okta or Azure AD with MFA (WebAuthn passkeys as primary factor). Device trust — Intune or Jamf for device management. Enforce corporate device + compliant posture (OS patch level, disk encryption, no jailbreak/root). Policy engine — define contextual policies: if user=HR AND device=managed AND location=office → access HR app. If user=HR AND device=managed AND location=home → access HR app via browser isolation (render in cloud, user sees pixels). If user=HR AND device=unmanaged → deny access to HR app. Access proxy — deploy Cloudflare Access or Zscaler ZPA in front of all internal apps (cloud and on-prem). All traffic routes through the proxy — no direct network access to applications. Network enforcement — micro-segmentation via Cilium in Kubernetes clusters and security groups in cloud. No implicit trust between VPCs or clusters. Data protection — encrypt all data at rest (AES-256, KMS-managed keys) and in transit (mTLS for service-to-service, HSTS for user-to-app). Monitoring — log all access decisions, analyze for anomalous patterns (access from unusual locations, unusual data access volume, access outside working hours). Use SIEM for correlation and alerting.

**Q5: How do you handle legacy applications that don't support modern authentication protocols?**

Candidate: Legacy apps (internal ERP, finance systems, old web apps) often support only LDAP auth, NTLM, or form-based authentication with local user stores. Approaches: (1) Reverse proxy with authentication — deploy a reverse proxy (nginx, Cloudflare Access, Pomerium, or OAuth2 Proxy) in front of the legacy app. The proxy handles modern auth (OIDC, SAML). After authentication, the proxy injects the user identity into the request via headers (X-Forwarded-User, X-Auth-Request-Email) or cookies. The legacy app reads the header and trusts it (local access rule ensures only the proxy can reach the app). (2) Sidecar agent — install an agent alongside the legacy app that intercepts authentication requests and translates between modern protocols and the legacy mechanism. (3) VPN with restrictions — as a temporary measure, restrict access to a VPN with JIT access (approved users get time-limited VPN access). This is NOT zero trust but bridges the gap while migrating to a proxy-based solution. (4) Application modernization — use the legacy app as a driver to migrate to a modern alternative that supports SSO and integrates with your identity provider.
