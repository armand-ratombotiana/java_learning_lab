# Mock Interview — SAML Federated Identity

## Interviewer: Identity Architect (45 min)

**Q1: Walk me through the SAML 2.0 SSO flow from end to end.**

Candidate: The flow starts when a user attempts to access a resource at the Service Provider (SP) without an active session. The SP generates an AuthnRequest — an XML document signed with the SP's private key, containing the SP entity ID, the Assertion Consumer Service (ACS) URL, a unique request ID, and optionally the NameID format and requested authentication context. The SP redirects the user to the IdP's SSO endpoint via HTTP Redirect binding (the AuthnRequest is base64-encoded and URL-params). The user authenticates at the IdP — login form, MFA, etc. The IdP generates a SAML assertion: an XML document containing the Subject (identified by NameID, usually email or persistent identifier), Conditions (NotBefore and NotOnOrAfter timestamps, AudienceRestriction specifying the SP entity ID, and optionally SubjectConfirmation), AttributeStatement (user attributes like email, firstName, groups, roles), and AuthnStatement (when and how the user authenticated). The IdP signs the assertion and optionally encrypts it for the SP. The IdP sends the response to the ACS URL via HTTP POST binding — the SAMLResponse (base64-encoded) is submitted via a form auto-submitted by JavaScript. The SP validates: (1) response signature (using IdP's public key from metadata). (2) Assertion conditions (timestamps valid, not expired). (3) Audience restriction matches the SP. (4) SubjectConfirmation method and data. (5) Replay prevention (check AssertionID against used IDs cache). If valid, the SP creates a session, extracts user attributes, and the user is logged in.

**Q2: What are the critical SAML security vulnerabilities and how do you mitigate each?**

Candidate: XML Signature Wrapping — the attacker modifies the SAML XML structure while keeping the signature valid. An XML signature covers a specific element (identified by ID reference). The attacker can copy the signed assertion, modify an unsanitized copy, and reference the original in the signature. Libraries that process the first matching element instead of the signed one get the modified assertion. Mitigation: use libraries that strictly follow the EXI reference processing rules — reject responses where the signed element is not exactly the one used. Validate the entire response structure. Timestamp validation — validate NotBefore and NotOnOrAfter with a 5-minute clock skew allowance. Reject assertions outside the validity window. Replay attacks — an attacker captures a valid SAML response and replays it. Mitigation: track AssertionID in a cache; reject duplicates within the validity window. For one-time use, invalidate the assertion after first consumption. Recipient mismatch — validate that the SAML response's Destination attribute matches the SP's ACS URL exactly. Validate that the Audience in the assertion matches the SP's entity ID. Certificate management — use strong keys (RSA 2048+ or ECC P-256), rotate certificates with overlap (new and old cert in metadata), validate certificate chain if signed by an intermediate CA.

**Q3: Compare SAML 2.0 with OpenID Connect for enterprise SSO.**

Candidate: SAML 2.0 is XML-based, uses HTTP POST/Redirect bindings for browser-based flow, and supports complex enterprise features: IdP-initiated SSO (user starts at IdP portal and clicks into apps), attribute queries (IdP returns user attributes on-demand), session management hooks, and long-standing in enterprise infrastructure (ADFS, Shibboleth, SimpleSAMLphp). OIDC is JSON-based, built on OAuth 2.0, uses JWTs for ID tokens, and is REST-friendly with simpler client libraries. OIDC supports dynamic client registration, discovery via .well-known/openid-configuration, and has better mobile/SPA support through PKCE. Choose SAML when: integrating with legacy enterprise IdPs, government systems (many require SAML), or applications with IdP-initiated SSO requirements. Choose OIDC for: modern applications (web, mobile, APIs), greenfield projects, and consumer-facing identity where you want simpler integration.

**Q4: How does single logout (SLO) work and what are the implementation challenges?**

Candidate: SLO ensures that logging out of one application logs the user out of ALL applications in the federation. SP-initiated SLO: user clicks logout at SP. SP sends LogoutRequest to IdP (signed). IdP terminates the user's session, then iterates over all registered SessionParticipants (other SPs with active sessions for this user) and sends a LogoutRequest via HTTP-POST or Redirect binding to each SP. Each SP terminates its local session and responds with a LogoutResponse. After all responses received (or timeout), IdP sends the final LogoutResponse to the initiating SP. Challenges: (1) User may have many sessions across many SPs — each redirect takes time. (2) Some SPs may be unavailable, causing the SLO to hang. (3) Mobile apps may not support SAML SLO. (4) Browser popups blocked by ad blockers. (5) Incomplete SLO weakens security — user thinks they're logged out but some sessions persist. Mitigation: use iframe-based SLO (hidden iframes for each SP), timeouts (complete what you can within 30 seconds), and display a "SLO complete" page that warns about incomplete SLOs.

**Q5: Design a SAML identity provider for a large enterprise.**

Candidate: Metadata — expose IdP metadata XML at a URL (entity ID, SSO endpoint, SLO endpoint, signing certificate, encryption certificate). Support export as XML. AuthnRequest handling — validate request signature, extract authn context (what type of auth is requested — password, MFA, X.509). Authentication — integrate with corporate identity store (Active Directory, LDAP), enforce MFA for high-risk apps, support step-up authentication. Assertion generation — build signed assertions with: NameID (persistent or email), SubjectConfirmation (holder-of-key or bearer), Conditions (validity window, audience, proxy restrictions), Attributes (user attributes from directory via configurable mapping). Sign with RS256 using HSM-stored key. Support encryption — encrypt assertions for specific SPs (using SP's public key from metadata). Session management — maintain IdP session, track participating SPs via SessionIndex, enforce session timeout. SLO — maintain session registry, propagate logout to all participants. Key management — generate keys in HSM, automate certificate rotation with overlap period, publish new certificates in metadata before old ones expire.
