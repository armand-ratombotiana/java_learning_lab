# Mock Interview — Authorization & RBAC

## Interviewer: Security Architect (40 min)

**Q1: Compare RBAC, ABAC, and ReBAC — when would you use each?**

Candidate: RBAC (Role-Based Access Control) assigns users to roles, and roles have permissions. Simple, intuitive, well-understood. Works well when roles are stable and well-defined (Admin, Editor, Viewer). Problems: role explosion — every new permission requires new roles, leading to hundreds of roles. RBAC is flat — you can't express "managers can approve expenses up to $10,000, directors up to $100,000" without creating 10 different roles. ABAC (Attribute-Based Access Control) uses policies based on user attributes (department, clearance), resource attributes (classification, owner), environment attributes (time, location), and action attributes (read, write). Extremely granular and flexible. Policy: "Allow read if user.department == resource.department AND user.clearance >= resource.classification AND time within business hours." Uses a policy engine like OPA (Rego language) or AWS Cedar. More complex to manage — policies need careful testing. ReBAC (Relationship-Based Access Control) makes decisions based on relationships between entities: "User is a member of Org, Org owns Document — User can edit Document." Used by Google Drive, Facebook, and GitHub. Expressive for social/multi-tenant apps but can be complex to implement. Google's Zanzibar (consistent, global authorization system) is the reference implementation. In practice: most applications start with RBAC, add ABAC for edge cases, and consider ReBAC for complex multi-tenant scenarios.

**Q2: Design an RBAC database schema for a SaaS application with organizations.**

Candidate: Tables: organizations (id, name, settings). users (id, email, org_id FK to organizations). roles (id, org_id FK, name, description — e.g., "Admin", "Editor", "Viewer"). permissions (id, resource [like "documents", "settings", "users"], action [like "read", "write", "delete", "admin"]). role_permissions (role_id FK, permission_id FK — many-to-many). user_roles (user_id FK, role_id FK, assigned_by, assigned_at, expires_at nullable). This schema allows organization-scoped roles. For inheritance: add archieved_roles table (role_id FK, parent_role_id FK) to model role hierarchies — Admin inherits Editor permissions. For resource-scoped permissions: add a resource_id column to role_permissions for fine-grained access (e.g., user has "Editor" role only on "Project X"). Implementation pattern: middleware extracts user ID from JWT/session, loads user's roles from the user_roles table (cached in Redis), loads all permissions for those roles, checks if the required permission (resource:action) is in the user's permission set. Cache roles with organization context for 5 minutes.

**Q3: How do you implement least privilege in a microservice architecture?**

Candidate: Each microservice has a principal identity — for Kubernetes: a service account. The service account is granted ONLY the permissions needed for that service's function. Service A (calling Service B): Service A's service account has permission to invoke Service B's specific endpoint. Service B's service account has permission to read from its database. Communication uses mTLS with SPIFFE identities (every service has a unique identity based on its workload). The API gateway validates coarse permissions (is this service allowed to reach this endpoint?), and each service validates fine-grained permissions. Use OAuth 2.0 scopes or JWT claims for service-level authorization. Implement the principle of strangulation — start with broad permissions, gradually restrict as you understand what's actually needed. Audit tools like IAM Access Analyzer identify over-permissioned roles. Automate permission review quarterly — flag roles with unused permissions for reduction. For human access: JIT (Just-In-Time) elevation — developers request temporary access for specific operations, automatically revoked after the task completes.

**Q4: What's the difference between vertical and horizontal privilege escalation? How do you prevent each?**

Candidate: Vertical privilege escalation (privilege elevation): a low-privileged user gains higher privileges than intended. Example: user with "viewer" role modifies their role to "admin" via API call. Prevention: server-side role enforcement (never trust client-provided role claims without server validation), use signed/opaque tokens for role assignments, validate role changes via an authorization server, implement audit trails for all role assignments. Horizontal privilege escalation (lateral access): user A accesses user B's data at the same privilege level. Example: user views invoice #123, changes the ID to #124 and sees another user's invoice. Prevention: ownership checks — every access control check verifies the authenticated user owns or is authorized for that specific resource. Use indirect references (UUIDs) instead of sequential IDs. Implement object-level access control — check user_id against resource.owner_user_id on every read/write. Techniques: data-scoped queries (WHERE owner_id = :userId), tenant isolation in multi-tenant systems, resource-level permissions in RBAC/ABAC. Penetration test specifically for IDOR (Insecure Direct Object Reference) vulnerabilities.

**Q5: Design a system for temporary elevated access (JIT access).**

Candidate: User requests elevated access via a portal selecting: role, duration (15 min, 60 min, 4 hours, 8 hours), justification (ticket number, incident ID), target resource (specific server, database, admin console). If the requested role requires approval (e.g., "super-admin"), the request routes to an approver (manager, security team) via Slack/email with approve/deny buttons. Approval threshold: for low-sensitivity elevation (dev environment), auto-approve. For production or sensitive data, require one or two approvals. Once approved: the role is granted for the specified duration with an automatic expiry. The system creates a temporary role binding, logs the elevation in the audit trail, and sends a notification. On expiry: the role binding is automatically removed, the elevated session is terminated. Active monitoring: during the elevated period, log all actions performed. If anomalous activity is detected, trigger an alert and revoke the access immediately. Audit report: monthly review of all JIT elevations — who, what, when, why. Unusual patterns (frequent short elevations, after-hours elevations flagged) are investigated. Integrate with PIM tools: AWS IAM Identity Center, Azure AD Privileged Identity Management, or OPA for custom implementations.
