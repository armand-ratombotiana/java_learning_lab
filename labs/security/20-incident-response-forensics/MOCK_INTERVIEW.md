# Mock Interview — Incident Response & Forensics

## Interviewer: Incident Response Lead (45 min)

**Q1: Walk through the complete incident response lifecycle using the NIST SP 800-61 framework.**

Candidate: Preparation — maintain an IR plan with defined roles (incident commander, technical lead, communications lead, legal, HR). Have tools ready: EDR (CrowdStrike, Defender), SIEM (Splunk, Sentinel), forensic acquisition tools (FTK Imager, LiME for memory, dd/dc3dd for disk), analysis tools (Volatility for memory, autopsy/sleuthkit for disk), and communication templates. Conduct tabletop exercises quarterly. Detection and Analysis — alert comes from EDR (malware detected), SIEM (correlation rule triggered), or user report (phishing). Triage within 15 minutes: validate the alert (real incident or false positive?), determine initial severity (low/medium/high/critical based on data sensitivity and system criticality), gather preliminary evidence (alert context, affected users/systems, timeline). Containment — Short-term: isolate affected hosts (network ACL block, EDR isolation), disable compromised accounts, block C2 infrastructure. Long-term: patch vulnerabilities, rotate credentials, update firewall rules. Eradication — remove malware and persistence mechanisms (scheduled tasks, service, WMI subscriptions, registry run keys), rebuild affected systems from clean images (never trust an infected system after cleanup), validate no remaining access. Recovery — restore data from clean backups, monitor for recurrence, gradually return to production. Lessons Learned — root cause analysis (RCA), timeline reconstruction, determine what went wrong and what went well, implement preventive controls, produce post-incident report for stakeholders. Calculate metrics: MTTD (Mean Time to Detect), MTTR (Mean Time to Respond), MTTI (Mean Time to Investigate).

**Q2: You receive an alert for ransomware encrypting files on a file server. Walk through the first hour step by step.**

Candidate: Minute 0-5 — Verify the alert. Confirm with the affected user: files have .locked extension, ransom note appears. Take a screenshot of the ransom note (contains variant details, payment instructions, and usually a Tor chat link). Minute 5-15 — Containment: disable the network interface on the affected server (via hypervisor or network switch isolation), disable the affected user's account (likely infection vector was their workstation), block outbound SMB traffic from the affected subnet. Minute 15-25 — Triage: isolate the server, take a memory image before reboot (use EDR to pull memory dump if available), capture network packets from the file server for the last hour. Check if backups are encrypted (verify backup system is separate and was not connected). Minute 25-40 — Determine scope: check which shares were accessible from the affected server, check if other servers show similar symptoms, review EDR for lateral movement activities from the initial host, review DNS logs for C2 communications. Minute 40-50 — Notification: notify management, legal, and PR teams (per your IR plan escalation matrix). Do NOT disclose details externally yet. Minute 50-60 — Engage remediation: identify the ransomware variant from the file extension and ransom note (helps determine if decryption tools exist, e.g., via NoMoreRansom project). Begin restoring priority data from clean backups to a clean, isolated environment. Never pay the ransom.

**Q3: How do you acquire forensic evidence from a compromised Linux server while maintaining chain of custody?**

Candidate: Order of volatility — capture the most volatile evidence first. (1) Memory acquisition: before any commands, capture RAM using LiME (Linux Memory Extractor) or AVML (Linux Memory Grabber). Load the kernel module and dump to an external destination (NFS share or network socket). Verify hash of the memory dump. (2) Network state: capture active connections (/proc/net/tcp, ss -anp, netstat -tulpn), ARP cache, routing table, iptables rules. (3) Process information: capture full process list (ps auxf), open file handles (lsof, fuser), loaded kernel modules (lsmod). (4) User information: currently logged-in users (w, who, last), login history (lastb, lastlog), sudo history. (5) System information: hostname, OS version, kernel version, system time (critical for timeline), uptime. (6) File system: capture with dd or dc3dd (better error reporting) to an external drive, not to the compromised system's disk. Capture important artifacts: ~/.bash_history (with timestamps if HISTTIMEFORMAT=set), /var/log (auth.log, syslog, kernlog), /etc/cron*, /etc/rc.local, /tmp contents, SSH authorized_keys. Chain of custody: document every action with timestamp, tool used, purpose, and output hash. Store evidence on write-protected media. Use a tamper-evident storage. Maintain a chain of custody form: who collected what, when, where, how, and who has access.

**Q4: How do you analyze a Windows memory dump for signs of compromise using Volatility 3?**

Candidate: Step 1 — Identify the OS profile: windows.info cmd for image information. Step 2 — Process analysis: windows.pslist enumerates processes. Cross-reference with windows.psscan (which finds hidden/unlinked processes by scanning pool tag) and windows.thrdscan (thread analysis). Look for: processes with no parent (possible injected code), processes running from temp directories, unexpected processes (powershell.exe launched from Word, svchost.exe with unusual PID). Step 3 — DLL analysis: windows.dlllist per suspicious process. Look for unsigned DLLs loaded into signed processes (DLL sideloading), DLLs loaded from temp directories, unusual count of loaded DLLs. Step 4 — Code injection: windows.malfind scans for executable code in non-executable memory regions or modified executable regions. Detects: process hollowing (legitimate process's code replaced), reflective DLL injection (DLL loaded without LoadLibrary). Step 5 — Network connections: windows.netscan lists active network connections and listening ports. Look for connections to known malicious IPs from threat intel feeds. Step 6 — Command line: windows.cmdline shows process launch arguments. Look for: encoded PowerShell commands (-EncodedCommand), suspicious base64, execution of remote scripts (IEX (New-Object Net.WebClient).DownloadString(...)). Step 7 — Registry extraction: windows.dumpfiles. Run YARA scans against memory for known malware signatures. Cross-reference findings with the timeline from other log sources.

**Q5: What's the difference between MTTD, MTTR, and MTBF in the context of incident response?**

Candidate: MTTD (Mean Time to Detect) measures the average time from when a security incident begins to when it is discovered by the security team. A SQL injection attack starts at 2:00 AM and is detected at 6:00 AM → MTTD is 4 hours. Goal: minimize MTTD. Industry: organizations with EDR and 24/7 SOC achieve MTTD of 30-60 minutes. Without 24/7 SOC: 24-48 hours. MTTR (Mean Time to Respond) measures the average time from detection to containment/remediation. After detection at 6:00 AM, the analyst isolates the affected host at 6:45 AM → MTTR is 45 minutes. Goal: minimize MTTR through automation (SOAR playbooks automate containment — isolate host, block IP, disable user). The full remediation (cleanup, patching, restoration) may take days, but containment time is the critical MTTR metric. MTBF (Mean Time Between Failures) in security context: average time between security incidents. Goal: maximize MTBF. Improving all three: MTTD improved by: better detection rules, 24/7 coverage, threat intelligence integration. MTTR improved by: automated playbooks (SOAR), pre-approved containment actions, on-call rotations, clear escalation paths. MTBF improved by: vulnerability management program, security awareness training, secure-by-default configurations, penetration testing.
