# Mock Interview — Supply Chain Security

## Interviewer: Security Engineer — Platform Security (45 min)

**Q1: What is a Software Bill of Materials (SBOM) and why is it critical for modern security?**

Candidate: An SBOM is a machine-readable inventory of all components in a software artifact — libraries, dependencies, tools, versions, and their transitive dependencies. Formats: CycloneDX (OWASP, most comprehensive — includes license info, vulnerability data, component metadata) and SPDX (Linux Foundation, focused on license compliance). Why critical: the Log4Shell vulnerability (CVE-2021-44228, December 2021) demonstrated the problem perfectly — within hours of disclosure, security teams worldwide were scrambling to find where Log4j was used. Organizations with SBOMs could query their inventory and identify affected systems in minutes. Without SBOMs, teams spent weeks manually checking build files, container images, and running servers. SBOMs enable: automated vulnerability scanning, rapid incident response, license compliance verification, and supply chain risk analysis. The US Executive Order on Cybersecurity (May 2021) mandates SBOMs for all software sold to the US government, making them a compliance requirement.

**Q2: Design a defense against dependency confusion attacks.**

Candidate: Dependency confusion occurs when a developer uses a private package name that also exists on a public registry (npm, PyPI, Maven Central). An attacker uploads a malicious package with the same name and a higher version number. The package manager, configured with the public registry as a fallback, picks the higher-version public package and installs the attacker's malware. Defense layers: (1) Scoped/namespaced packages — npm uses @company/package-name. Maven uses reverse domain groupId (com.company.package). This prevents naming collisions because scopes are unique. (2) Registry configuration — for npm, set .npmrc: @myco:registry=https://internal-registry. For Maven, mirror all registries through a single private repository manager (Nexus, Artifactory) that resolves from a curated set of approved public packages. (3) Dependency verification — use lockfiles (package-lock.json, yarn.lock, poetry.lock) with integrity hashes (subresource integrity). The lockfile pins the exact version and hash — any substitution is detected. (4) Integrate package availability monitoring — a tool that alerts if a private package name becomes available on a public registry (indicates someone is trying the attack).

**Q3: Explain SLSA (Supply-chain Levels for Software Artifacts) and how to achieve each level.**

Candidate: SLSA is a security framework that defines integrity levels for software supply chains. SLSA 1 (Documented): the build process is documented, and provenance (metadata about how the artifact was built) is generated. At this level, you know what was built and when, but the provenance isn't verified. SLSA 2 (Hosted build): the build runs on a hosted platform (not a developer's laptop) — GitHub Actions, GitLab CI, or Jenkins with clean workspace. The provenance is signed by the build platform. This prevents "works on my machine" issues and provides a verifiable chain. SLSA 3 (Hardened build): builds are hermetic (no network access except pre-approved), build steps are defined in code (not UI), and the provenance includes the exact build script hash. The build platform enforces isolation between builds. SLSA 4 (Two-person review): every change requires two-person review before merging, the build process is auditable and reproducible (same inputs produce same output), and the provenance includes all build dependencies. Adopting SLSA is incremental — start with SLSA 1 (generate provenance), then move to hosted builds (2), then harden the build environment (3), and finally enforce two-person review and reproducibility (4).

**Q4: How do you implement Sigstore/Cosign for container image signing in a CI/CD pipeline?**

Candidate: Sigstore provides free, open-source software signing with three components: Cosign (CLI for signing containers and blobs), Fulcio (free root certificate authority for keyless signing), and Rekor (transparency log for recording signatures). Implementation: (1) Install Cosign in the CI pipeline. (2) For keyless signing (recommended): use OIDC — the CI job authenticates via its OIDC identity (GitHub Actions, GitLab CI). Cosign obtains a short-lived signing certificate from Fulcio, signs the image, and the signature is recorded in Rekor. No long-term key management needed. Command: cosign sign --yes $IMAGE. (3) For key-based signing: generate a key pair, sign with cosign sign --key cosign.key $IMAGE, store the public key in a Kubernetes Secret. (4) Verification at deploy time: configure an admission controller (Sigstore Policy Controller or Kyverno) that verifies signatures before allowing deployment. Command: cosign verify --key <public-key> $IMAGE. The policy controller rejects unsigned images or images with invalid signatures. (5) Attestation: go beyond signing with cosign attest to generate in-toto attestations containing SBOM, SAST results, and test results. Verify attestations before deployment.

**Q5: Design a secure software supply chain pipeline from code commit to production deployment.**

Candidate: Stage 1 — Source: branch protection with required reviews (2 approvals for main). Signed commits (GPG or SSH). Secrets scanning on every push (truffleHog, GitLeaks). Stage 2 — Build: trigger on PR merge. Checkout code, build in clean environment (no cached artifacts from untrusted sources). Run SAST (Semgrep, CodeQL) — fail on critical/high findings. Run unit and integration tests. Dependency scanning — generate SBOM (CycloneDX), scan with OWASP Dependency-Check, fail on critical CVEs with known exploits. Stage 3 — Package: build container image with pinned base image and digest. Scan image with Trivy — fail on critical/high CVEs. Sign image with Cosign (keyless). Generate provenance (SLSA) — attach as attestation. Push to private registry. Stage 4 — Deploy: admission controller validates: (1) Image signature verified (Cosign). (2) No critical CVEs in image scan. (3) Sbom attestation present. (4) Build provenance at SLSA 3+. Apply network policies and security context. Stage 5 — Monitor: post-deployment scanning — continuous container scanning (Registry scanning). Runtime detection (Falco) for anomalous behavior. Dependency monitoring — alert on new CVEs for deployed dependencies. Automatically create tickets for critical CVEs requiring patch in 48 hours.
