# Lab 15: Mock Interview — Production ML Architecture

**Role**: ML Platform Engineer
**Duration**: 60 minutes
**Focus**: End-to-end ML platform design (ingestion, feature store, registry, serving, monitoring, CI/CD), case-study simulation, SLOs and alerting thresholds, deterministic simulation, multi-tenant platform concerns, production gaps and how to close them

---

**Interviewer**: "Start with the blueprint. The lab wires seven components into `MLPlatformBlueprint` — what does each one actually own, and how do they fit together?"

**Candidate**: "The blueprint is a dependency graph of the production ML lifecycle. `DataIngestion` owns the boundary — a source and format (Kafka: transactions/Avro for fraud, S3: user_events/Parquet for recommendations, Event Hub + S3/Delta Lake for the multi-tenant platform) — and its `ingest()` answers 'what just arrived and how is it encoded'. `FeatureStore` owns the two access patterns every platform needs: an online map keyed by entity for sub-millisecond serving lookups, and an offline append log for training. `ModelRegistry` owns lifecycle state — `register` always lands a model in `Staging` with an artifact URI, and `getProductionModel` is an `Optional` read, which is the right contract for 'the production model may not exist'. `ServingInfrastructure.scale` is the autoscaler, `MonitoringSystem` is the SLO brain (record, average, alert), and `CiCdPipeline.run` is the release gate. `MLPlatformBlueprint.simulate()` is the integration test: one `Random(42)` driving 1,000 simulated predictions through monitoring, then printing alerts and averages. It's the capstone lab precisely because every earlier lab maps to a component — Lab 01 to ingestion, Lab 02's tracking to the registry, Lab 08's drift to the monitor, Lab 12's IaC to the serving layer."

**Interviewer**: "Why two maps in `FeatureStore` — `online` and `offline` — and why those exact structures?"

**Candidate**: "Because the read patterns are structurally different. Online serving is point reads at request time: `online` is a `ConcurrentHashMap<String, Map<String, Object>>` keyed by entity ID, updated by `writeOnline` and read by `readOnline`, which returns `Map.of()` as a safe default for a key that was never written — the caller never has to null-check. Offline training is an append log: `writeOffline` uses `computeIfAbsent(partition, ...)` so the first write to a partition creates the list and every later write appends, and `readOffline` replays the partition in write order. That's the classic online/offline duality — Redis-style point store for the hot path, S3-style partition log for the batch path — and the lab models both with two tiny collections. The `Map<String, Object>` value type is deliberately heterogeneous: feature vectors genuinely mix doubles, longs, and strings, which is exactly why the walkthrough keeps every numeric read behind `((Number) ...).doubleValue()` — a single conversion point instead of scattered casts."

**Interviewer**: "`ModelRegistry.promote` is a stub — the comment says 'promote logic here' and it does nothing. `getProductionModel` therefore never returns a model. What's the lesson?"

**Candidate**: "It's an honest empty function, and that's the lesson: promotion is a governance decision, not a data structure operation. Real promotion is an API call that requires permissions, writes an audit entry (Lab 11's audit-trail integrity), updates the model card's stage field, and triggers the deployment pipeline — the lab's `forEach` with an empty body is the placeholder where that approval workflow lives. The consequence is visible in the API contract: `getProductionModel` returns `Optional<ModelRecord>` precisely because 'there is no production model yet' is a normal, expected state — not an exception. The walkthrough's governance question — who can call `promote`, and what does the audit log capture — is the actual design work. A registry without a working promotion path is a library of candidates; the demo shows how easy it is to build the catalog and how hard it is to wire the approval chain."

**Interviewer**: "`ServingInfrastructure.scale` computes `min(maxReplicas, max(1, load / 1000))`. Walk through the three case studies' results — 5→5, 3→5, and 20→5."

**Candidate**: "All three platforms simulate 5,000 req/s, so `load / 1000` is 5. The fraud platform starts at 5 with `maxReplicas = 20` → `min(20, 5)` = 5, no change. The recommendation engine starts at 3 with `maxReplicas = 10` → scales up to 5. The multi-tenant platform starts at 20 with `maxReplicas = 100` → scales *down* to 5, which is the interesting case: scaling logic must handle both directions, and at the same 5,000 req/s that the smaller platforms are growing into, the big platform is shedding 15 replicas. That's the HPA analog — a proportional controller, `ceil(load / perReplicaCapacity)` with `max(1, ...)` as the floor and `min(maxReplicas, ...)` as the ceiling. The lesson is in the seams: the floor exists so a single-request load doesn't scale to zero, the ceiling exists so a load spike doesn't blow the budget, and the real product would use `targetCpuUtilization` (field present, unused in the demo) to drive the controller instead of a fixed divisor — the lab gives you the shape of the autoscaler, and production adds the feedback metric."

**Interviewer**: "The monitoring output is identical across all three case studies: `error_rate=0.012, latency_p99=184.16516737784085, drift_psi=0.20122142265534781`. Why identical, and why those particular numbers?"

**Candidate**: "Identical because each `simulate()` seeds its own `Random(42)`, so the same 1,000-prediction sequence plays out three times — deliberate reproducibility, same pattern as Lab 10's seeded bandit and Lab 13's seeded workers. The values come from the three generators: `latency = 50 + |gaussian| * 30`, recorded as `min(500, latency * 2.5)` — that 2.5× factor models the tail: the p99 of a right-skewed latency distribution sits above the mean, so `184.17 ms` is the tail metric while the typical request is nearer 50–80 ms. `error` is a Bernoulli with `p = 0.02`; the observed `0.012` is a 1,000-sample estimate — 12 errors out of 1,000 — within sampling variance of 20, and that variance is the point: a 2% error rate can easily measure as 1.2% on one day's traffic, which is why alerting needs windows and baselines, not single runs. `drift = 0.1 + rand * 0.2` is uniform on [0.1, 0.3), averaging 0.2 — the measured 0.201 is again the finite-sample estimate. The trio is deliberately composed: one metric breaches its threshold, two don't."

**Interviewer**: "Check the alerts: `⚠ Alerts: High error rate`. Why exactly one alert, and why is the answer three threshold comparisons?"

**Candidate**: "`checkAlerts` runs three independent comparisons against the averages — `latency_p99 > 200`, `error_rate > 0.01`, `drift_psi > 0.25` — and collects matches into a list. With `184.17 ≤ 200`, `0.012 > 0.01`, and `0.201 ≤ 0.25`, exactly one condition fires: high error rate. Two details matter. First, the thresholds encode the SLOs: fraud detection at 10K tps budgeted P99 under 50 ms (the platform description says so!) yet the simulated average is 184 ms — the alerting system and the declared SLA disagree, and a good interviewer question is whether the model or the target is wrong; in production you'd alert on *both* the absolute value and the distance from the SLA. Second, the drift threshold at 0.25 is Lab 08's PSI thinking carried forward: 0.201 is 'moderate' per the PSI rubric, below the critical line, so no drift alert — but the platform doesn't log that the metric *approached* the threshold. Alerting on breach is table stakes; trending toward breach is the production feature."

**Interviewer**: "The CI/CD pipeline prints seven steps and ends with '⏸ Manual approval required for production', but `simulate()` only prints `cicd.run().get(2)` — the model training line. Why?"

**Candidate**: "Because `simulate()` is a case study, not a full pipeline trace — one representative line per component keeps the output readable, and training (`accuracy=0.947`) is the most informative line of the seven. But the full list is the real content, and it tells a release story: code checkout, data validation (Lab 09's validator as a gate), training, evaluation against the champion — `0.947 > 0.935`, so the challenger wins — staging deploy, integration tests, and then manual approval. That ordering is the CI/CD discipline this course has drilled in every lab: validation gates in Lab 07, drift gates in Lab 08, model cards in Lab 11, IaC in Lab 12. The manual approval step is the deliberate seam: automated everything except the final human decision on production promotion — which is also why `ModelRegistry.promote` is a stub: the pipeline asks for approval, the registry waits for the approval, and the lab models both halves of that handshake."

**Interviewer**: "The feature store and monitoring use `ConcurrentHashMap` and `CopyOnWriteArrayList`. What's actually concurrent in this platform, and what's the thread-safety reasoning?"

**Candidate**: "The concurrency is where the lab's realism shows. Online serving is concurrent by construction: a fraud platform at 10K tps has thousands of in-flight requests reading `readOnline` while training jobs `writeOffline` and feature writers `writeOnline` — so the online map is `ConcurrentHashMap` (lock-striped, safe concurrent reads and writes), and the offline log is a plain map of lists because each partition write happens in one thread; `computeIfAbsent` makes the first-write race safe. Monitoring uses `CopyOnWriteArrayList` per metric because `record` is a high-frequency append and reads (`getAverages`) are rare — copy-on-write trades write cost for lock-free reads, the right trade for a telemetry stream. The subtlety the demo can't show: `getAverages` iterates the `ConcurrentHashMap` weakly consistent, which is fine for a snapshot average — but the printed order (error_rate, latency_p99, drift_psi) is iteration order, stable on this JDK for three keys but not contractually guaranteed, which is why the walkthrough treats the transcript as an output contract. In production I'd replace the map-of-lists with an actual time-series store, but the concurrency *shape* — concurrent point writes, rare aggregated reads — is exactly right."

**Interviewer**: "Contrast the three case studies as SLAs: fraud at 10K tps with 'P99<50ms', recommendations for 100M users daily, and a multi-tenant platform serving 50 teams and 500 models. What does each change about the design?"

**Candidate**: "Fraud is a real-time path: streaming ingestion (Kafka, Avro), low-latency feature lookups that can't afford to miss (hence the `Optional`-style default read), and a latency budget in milliseconds — the 50ms target is the design driver, and the simulated 184ms p99 is the alarm bell. Recommendations are batch: 100M users *daily* means the workload is a scheduled job, not a request path — S3/Parquet ingestion, offline feature materialization, and the latency budget is hours, not milliseconds, so the *same* `MLPlatformBlueprint` with different parameters is the whole demo's point: the platform is one shape with pluggable profiles. Multi-tenant is the governance case: 50 teams share one registry and one serving cluster, so 500 models need namespacing, quota, isolation, and shared-SLA discipline — a noisy neighbor on the fraud platform burns one team's p99; on the multi-tenant platform it burns fifty teams'. The lab gives all three the same scale formula, which is a simplification worth stating aloud: real per-tenant platforms route by tenant and scale per service, not globally — but the shared blueprint is what makes the comparison legible."

**Interviewer**: "What doesn't the lab model that a production platform needs, and how would you rank the gaps?"

**Candidate**: "Four gaps, in priority order. First, real autoscaling feedback: the demo scales on a fixed `load/1000` divisor while the HPA-style fields (`targetCpuUtilization`, `maxReplicas`) sit unused — production would feed actual utilization into the controller, with hysteresis so the 20→5 scale-down happens in steps, not a cliff. Second, deployment strategy: the CI/CD pipeline ends at approval, but nothing models canary rollout, blue-green, or rollback — the registry's stages exist, the traffic shifting doesn't; Lab 10's A/B infrastructure is the natural extension. Third, alerting quality: `checkAlerts` is threshold-on-average, with no windows, no trend detection, no severity routing — the Lab 08 walkthrough already flagged the same limit, and here it matters more because the monitoring is the platform's only brain. Fourth, governance durability: promotion is a stub and there's no audit log object, so the registry can't answer 'who promoted what, when, with which approval' — Lab 11's integrity-checked entries would bolt on cleanly. Ranked that way, the feedback loop (1–2) is what keeps the platform serving; observability (3) and governance (4) are what keep it safe."

**Interviewer**: "You mentioned the outputs are a contract. How would you CI-test this blueprint so the transcript stays trustworthy?"

**Candidate**: "Three tiers, matching every other lab. Golden transcript: `simulate()` with `Random(42)` must reproduce the captured output — the three identical metric lines (`error_rate=0.012`, `latency_p99=184.16516737784085`, `drift_psi=0.20122142265534781`), the single `High error rate` alert, and the summary box — so any change to a generator, a threshold, or an RNG is a visible diff. Structural: 1,000 records land in each metric list; `getAverages` returns exactly the three keys; `scale(5000)` maps to `min(maxReplicas, max(1, 5))` for all three platforms — testing the floor and ceiling explicitly at `load=0` and `load=10⁷`. Behavioral: `checkAlerts` on a crafted state (latency 250, error 0.02, drift 0.3) returns all three alerts, and on the golden state returns exactly one — the threshold boundaries are the unit-test targets. That discipline is the capstone takeaway: a platform with a frozen transcript, tested boundaries, and seeded determinism is a platform you can refactor without fear."

**Interviewer**: "Final question — you're handed this blueprint as a new platform's starting point. What's the first production change you make, and why?"

**Candidate**: "Close the feedback loop: wire `targetCpuUtilization` into the scale controller and give `promote` a real, audited implementation — in that order. Scaling first, because the demo's hardcoded divisor is the only piece that makes the platform *wrong* under load: at 60% CPU and 5,000 req/s, a divisor-based controller either burns money or sheds traffic, and hysteresis keeps the multi-tenant 20→5 scale-down from flapping. Then promotion, because every model in the registry is currently stuck in Staging — the platform serves zero production models, which is the gap between 'demonstrates' and 'delivers'. After those two, I'd add canary deployment behind the CI/CD approval step and call the platform production-grade. And I'd keep the seeded `simulate()` as the golden-test harness for the whole evolution — the blueprint's greatest strength is that it can be tested from day one."
