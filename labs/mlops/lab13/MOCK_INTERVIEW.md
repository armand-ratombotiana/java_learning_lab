# Lab 13: Mock Interview — Distributed Training

**Role**: ML Platform Engineer / Distributed Systems Engineer
**Duration**: 60 minutes
**Focus**: Data vs model parallelism, ring all-reduce (scatter-reduce + all-gather), synchronous vs asynchronous training, scaling rules (batch size, learning rate), stragglers and fault tolerance

---

**Interviewer**: "Start with the training loop. What is the lab simulating, and how faithful is it to real distributed training?"

**Candidate**: "It's a miniature of data-parallel DDP — the pattern behind Horovod, PyTorch DDP, and DeepSpeed. One `globalModel` (64 weights, all initialized to 0.5); 1,000 samples sharded into 4 worker partitions of 250; each epoch the global weights are copied to 4 local models, the workers compute gradients in parallel over 128-sample batches, a `RingAllReduce` averages them, and the global model steps with the averaged gradients. The fidelity is high on the *communication* side — the ring's two phases and its O(N) per-worker cost are exactly what production systems do — and intentionally abstracted on the compute side: the worker's 'gradient' is a two-line formula over random samples, and the 200ms sleep stands in for GPU compute. What it gets right: the invariant that every worker ends an epoch with the same averaged gradient, and the loop structure: copy, compute, reduce, step."

**Interviewer**: "Explain the ring all-reduce as if to a new hire. Why is it O(N) per worker, and why does that matter?"

**Candidate**: "Two phases. Phase 1, scatter-reduce: the gradient vector is split into one chunk per worker — 64 params over 4 workers means 16-param chunks. For `nWorkers - 1` steps, each worker sends its chunk to its right neighbor, which *adds* it into its own chunk. After the ring makes a full lap, each worker holds one chunk that is the sum of that chunk's values from *all* workers. Phase 2, all-gather: another `nWorkers - 1` steps rotate the summed chunks around the ring with copies instead of adds, until every worker holds the complete sum. Then divide by `nWorkers` — done, every worker has the identical averaged gradient. The cost: each worker sends `2 × (nWorkers - 1)` chunks of size `N/nWorkers` — total `O(N)` elements regardless of how many workers. Compare that with a parameter server, where the server processes `N × nWorkers` elements and is the network and compute bottleneck — the ring is why you can scale to hundreds of GPUs."

**Interviewer**: "The lab's `DistributedWorker` computes gradients over *random samples from its shard* — sampling with replacement. What's the design choice there, and what would a real implementation do?"

**Candidate**: "The worker draws `batchSize` samples uniformly from its shard, so the 128-sample batch is a stochastic estimate of the shard's gradient — that's the SGD flavor, not full-batch GD. In the walkthrough the worker RNG is seeded per worker, which is important: unseeded, every run would compute different gradients and the loss curve wouldn't reproduce — the lab's original output is nondeterministic for exactly this reason. Real implementations shuffle the shard deterministically and consume windows in order, which keeps the batch distribution even; sampling with replacement is the simpler proxy that preserves the same stochastic-gradient math. Either way, the aggregate matters: each worker's noisy estimate is averaged by the ring, so the *mean* of the per-worker estimates is what steps the model — which is the whole point of data parallelism."

**Interviewer**: "Why does the global loss stay flat at 0.060098 in the walkthrough? Is that a bug?"

**Candidate**: "No — it's the honest physics of the toy problem. The data is uniform on [0,1) — per-dimension mean 0.5 — and the weights start at exactly 0.5, so the gradient `2(w - x)/N` has expected value zero on every batch. The model is already at the empirical optimum of that target, so the loss doesn't move; `0.060098` is the irreducible squared error of 0.5 against the particular sample `computeLoss` measures. The useful lesson: the ring still produces a correct averaged gradient — zero-in-expectation — and the flat curve demonstrates the machinery works. A better demo of *learning* would initialize weights away from the data mean (e.g., 0.1) or use a target function — but then the interesting part is the convergence curve, not the communication, and the lab chose communication as its subject."

**Interviewer**: "Synchronous vs asynchronous training — the lab's core Q. Where does the ring sit, and when do you choose which?"

**Candidate**: "The ring is the synchronous pattern: `invokeAll` waits for every worker's gradient, then one all-reduce, then a single step — the model is always the same on every node, which is what makes evaluation, checkpointing, and debugging sane. Asynchronous training drops the barrier: workers push gradients to a parameter server when ready and pull fresh weights when needed — higher throughput and natural resilience to stragglers, but the model is never a single snapshot, convergence can oscillate, and reproducibility suffers. The decision rule: correctness and determinism first — synchronous; throughput under heterogeneous or fault-prone nodes — asynchronous, accepting the looser semantics. Most production training is synchronous with backup workers: exactly the ring, plus spares to absorb stragglers."

**Interviewer**: "Scaling the recipe: 1 GPU batch 128 lr 0.01 becomes 8 GPUs. What changes?"

**Candidate**: "The effective batch becomes 1024 — the ring averages 8 per-worker gradient estimates, which equals the gradient of the concatenated batch. Two rules follow. Learning-rate scaling: gradient magnitudes grow roughly linearly with effective batch, so the linear scaling rule says `lr_8 = lr_1 × 8 = 0.08`; keeping 0.01 means 8× larger steps relative to the data — effectively an oversized step size. And variance: 8× batch cuts gradient noise ~√8, so the model may converge in fewer epochs, but extremely large batches can hurt generalization, which is why the rule is a starting point, tuned with warmup on validation loss — not a formula to apply blindly. The lab makes the mechanism visible: the same ring code, the same learningRate constant — changing the worker count changes the effective batch without touching the loop."

**Interviewer**: "A worker slows to 2s per epoch while others take 200ms. Walk through the impact and the fixes."

**Candidate**: "`executor.invokeAll` blocks until the slowest future completes — the epoch is 10× slower for everyone, every epoch. Fixes, in order of preference: backup workers — launch `n + spare` workers and use the first n results (the standard in large-scale training); shrink per-epoch variance — balance shard sizes and equalize work, since the lab's equal `subList` shards are already fair, but real shards aren't; and dynamic batching — give the straggler a smaller batch so its compute time matches. If the straggler is systematic (heterogeneous fleet), the honest answer is async training or per-node gradient accumulation. And all of this is *why* the ring is the right primitive: the reduction is O(N) per worker, so communication never hides the straggler — the scheduler has to fix the balance, not the network."

**Interviewer**: "Fault tolerance: a worker dies mid-epoch in real training. What protects the run, and what does this lab not model?"

**Candidate**: "Three layers. Elasticity: DDP implementations detect a dead worker and re-shard — the `shards` list is rebuilt over the remaining workers (the lab's `subList` construction is exactly the resharding point). Checkpointing: real training persists weights + optimizer state + epoch counter every N epochs, so a dead node restarts from the last checkpoint, not epoch 1 — the lab has no persistence because it has no state beyond 64 doubles. Restart orchestration: the training controller (Lab 07's pipeline) relaunches the job with the checkpoint; the ring is stateless per epoch, so it needs no repair — its per-epoch nature is itself the resilience property. What the lab *can* teach: `invokeAll` + `Future.get()` has no timeout, so a hung worker stalls forever — production code adds `get(timeout)` and treats it as a failed epoch."

**Interviewer**: "Model parallelism vs data parallelism — when does data parallelism stop scaling?"

**Candidate**: "Data parallelism replicates the whole model per worker, so it stops scaling when the model doesn't fit in one device's memory — that's the crossover for large LLMs, where each GPU holds a shard of the network instead of a shard of the data. Model parallelism splits layers or tensors across devices (pipeline parallelism = layer shards, tensor parallelism = intra-layer shards); it changes the communication from the ring's gradient averaging to activations and gradients flowing along the pipeline — much more bandwidth-heavy, which is why the lab's data-parallel ring is the right default and model parallelism is the specialist pattern. The lab is purely data-parallel; the `Model` with 64 weights is a reminder that the ring's O(N) cost is what lets data parallelism scale to worker counts where a parameter server would collapse."

**Interviewer**: "What would you test to prove the ring is correct?"

**Candidate**: "The ground-truth test: run `RingAllReduce.allReduce` on hand-computed inputs — say four small gradient vectors `{1,2}`, `{3,4}`, `{5,6}`, `{7,8}` — and assert every output equals the elementwise average `{4,5}`; that catches the classic chunking and modulo bugs in one shot. Structural tests: every output array is a deep copy (mutating one worker's input doesn't change others); with `nParams % nWorkers != 0`, the ragged edge is handled — 64/4 divides evenly, but 70/4 must still work; and an invariant check with random vectors: each output equals the average computed by a naive loop. Then the integration test: with seeded workers, the epoch-end global loss matches a golden transcript — the walkthrough's Expected Output *is* that test."

**Interviewer**: "Last one: the lab prints worker losses from `call()`; the walkthrough prints them from `main`. Why does that matter?"

**Candidate**: "Because `call()` runs on 4 threads that finish their 200ms sleeps within microseconds of each other, and `System.out.println` has no ordering guarantee — run the lab twice and the worker lines interleave differently. Printing from `main` after `future.get()` in the order of the `invokeAll` future list is deterministic by construction: futures are collected in submission order. It's a small example of a large principle in distributed systems — output and logging order are part of your contract, and race-free logging is what makes a golden transcript (and therefore a golden test) possible. In real distributed training this is the same reason rank-ordered logging exists: every rank prints its diagnostics in rank order, so the log is a stable artifact the cluster can diff against."
