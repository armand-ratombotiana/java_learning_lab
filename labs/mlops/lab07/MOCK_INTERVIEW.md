# Lab 07: Mock Interview — CI/CD for ML Pipelines

**Role**: MLOps Engineer / ML CI/CD Engineer
**Duration**: 60 minutes
**Focus**: ML pipeline gates, data-aware triggers, champion comparison, rollbacks, GitHub Actions vs Jenkins, model promotion

---

**Interviewer**: "Walk me through the lab's CI/CD model. What does `CiCdForMLPipelineLab` actually simulate?"

**Candidate**: "It simulates the eight-stage ML pipeline as a dependency-ordered list of `PipelineStage` objects — each with a name, `dependencies`, and a `Runnable action` — executed sequentially with a gate after every stage: `execute()` sets `passed` on success and the driver prints `✓ X passed` or `✗ X FAILED: reason`, skipping stages whose dependencies failed with `⧖ Stage: X — skipped (dependency failed)`. The stages are Code Checkout → Data Validation → Feature Engineering → Model Training (printing `Model trained with accuracy=0.947`) → Model Evaluation → Deploy Staging → Integration Tests → Deploy Production. Then the lab *generates* the same pipeline as a GitHub Actions workflow and a Jenkinsfile, so the simulation and the real CI/CD definition stay in one codebase."

**Interviewer**: "The Model Evaluation stage compares `accuracy 0.947` against `champion 0.935` and throws if it's lower. Why is that the right gate to put in CI, and what are the other gates?"

**Candidate**: "Because 'model trained' is not 'model good enough to ship'. The evaluation gate enforces a threshold against the *current production champion* — the interview notes call it champion-vs-challenger with a statistical significance test — so the pipeline self-rejects regressions instead of deploying them. The lab encodes it directly: `if (accuracy < champion) throw new RuntimeException("Accuracy " + accuracy + " < champion " + champion)` and prints `✓ Accuracy 0.947 > champion 0.935`. The complete gate stack per the interview notes: (1) data validation gate — schema and distribution checks (Lab 09), (2) evaluation gate — champion comparison, (3) shadow deployment — run the new model on shadow traffic for N hours, (4) manual approval for production. The lab's workflow shows the last one: the `deploy-production` job runs on the `production` environment, which in GitHub Actions means an approval gate."

**Interviewer**: "The pipeline is triggered on `push`, `pull_request`, and a weekly `cron`. What's missing for ML, and how do you trigger retraining on data?"

**Candidate**: "The lab's triggers are code-centric — the interview notes call out the second trigger class: data. A model is stale because the world changed, not because code changed, so retraining must trigger on data events: new data arrival, schema change from the validation layer, or drift detected by Lab 08's monitoring. The design: a scheduled job plus a webhook — data pipeline completion POSTs to the CI system, which starts data validation → retraining → evaluation. DVC versioning the dataset is the companion piece: data changes become reviewable diffs, and the training job pulls the pinned dataset version. So you end up with two pipelines sharing the same stages: code-change pipeline (push) and data-change pipeline (webhook/schedule)."

**Interviewer**: "How do you roll back a bad model deployment in this design — the lab's Q2?"

**Candidate**: "Rollback must be as automated as deployment. Every deployment is versioned — the CD pipeline knows the previous production model — and the rollback path is: re-tag the previous version as production in the MLflow registry (Lab 03's `promoteToProduction` on the old version — the immutable re-tagging pattern), and for Kubernetes `kubectl rollout undo deployment/<name>` reverts the pod template. The interview notes add a dedicated 'Rollback' pipeline job that reverts to the last successful production model, so the operator doesn't improvise during an incident. The critical property: because the registry history is immutable and the deployment artifacts are versioned, 'roll back' is a pointer change plus a rollout — not a rebuild."

**Interviewer**: "GitHub Actions vs Jenkins for ML — the lab's Q4."

**Candidate**: "GitHub Actions: cloud-native, simple YAML, great marketplace ecosystem — right for small-to-medium teams and for ML because the CI half (lint, unit tests, validation, training smoke tests) is well served by its hosted runners and cache. Jenkins: max flexibility — custom plugins, enterprise RBAC, audit trails, and full control over the CD half with approvals and complex promotion logic; right for regulated industries that need audit and for on-prem. The lab's own output encodes the split: it generates *both* — the Actions workflow for the cloud pipeline and a Jenkinsfile with a Groovy `error` gate on the champion comparison and a `when { branch 'main' }` production stage. My default: Actions for CI, and a CD system with approvals for production promotion."

**Interviewer**: "The Jenkinsfile compares `accuracy.toDouble() < champion.toDouble()` in Groovy. What's wrong with embedding the gate in the CI DSL, and where should it live?"

**Candidate**: "Logic in the DSL is untestable — you can't unit-test Groovy string interpolation the way you test Java. The gate should be a library function: the lab's evaluation logic (`0.947 vs 0.935`, threshold decision, error message) is the same decision in `CiCdForMLPipelineLab` and in both generated files, which is exactly the duplication risk. Production pattern: the evaluation runs in the training service or a shared validation library, publishes a structured result (model, metric, champion, pass/fail), and the CI system just consumes the decision and gates. The DSL stays a thin orchestrator: run step → read result → promote or fail. The lab keeps the gate in Java for the simulation and repeats it in YAML/Groovy for the demo — a deliberate lesson in why that duplication is a smell."

**Interviewer**: "The lab's stages run sequentially with dependency checks. What's wrong with a linear pipeline for ML, and when do you parallelize?"

**Candidate**: "A linear chain serializes independent work — data validation doesn't need training to finish, and feature engineering could start once validation passes. The guide's best practices call it out: parallelize independent stages (data validation + feature engineering) and use matrix builds for multi-model workflows. The lab's `PipelineStage.dependencies` list is the primitive that would let you branch — the interview notes' 'Design a Pipeline System' answer. But there's a deliberate conservative choice too: the model evaluation gate must be sequential after training, and production promotion after shadow testing — those edges are causal, not convenient. The rule: parallelize only what's truly independent; every merge point is a gate."

**Interviewer**: "What makes an ML pipeline stage idempotent, and why does CI/CD demand it — the best-practice list mentions it first?"

**Candidate**: "A stage is idempotent when running it twice with the same inputs produces the same result and the same state — no duplicate rows, no double-deployed models, no appended logs. CI/CD demands it because retries are the norm: a flaky runner, a timed-out job, a re-run after a fix — the pipeline restarts at a stage boundary, and a non-idempotent stage corrupts everything downstream. The ML specifics: training writes to versioned outputs keyed by run ID (Lab 02), feature computation overwrites its partition (Lab 04), registry registration is a fresh version each time (Lab 03) rather than an overwrite, and deployment stages use the registry's stage transitions. The lab's stages are idempotent by construction — that's why re-running the simulation produces identical output."

**Interviewer**: "The workflow's `training` job runs `javac` inside the runner. How would you improve the CI for a real training job?"

**Candidate**: "Three upgrades. Cache the dependencies — the guide explicitly lists caching Maven/Gradle and datasets, so a retrain doesn't re-download 50GB. Containerize the runner — the training job should run the same Docker image Lab 05 builds, so CI and production share the runtime. And split training from everything else: training is long and GPU-bound, so it runs on a self-hosted GPU runner or a separate training service, while validation and tests stay on fast hosted runners. The generated workflow shows the seed pattern — `actions/setup-java` with temurin 21 — but production training needs the artifact upload (`actions/upload-artifact` with the model) which the lab already includes, and that artifact is what the evaluation and registry stages consume."

**Interviewer**: "How does this lab connect to Lab 03's registry and Lab 08's monitoring for a closed loop?"

**Candidate**: "The CI/CD pipeline is the executor of decisions made by the other labs. Lab 03's registry gate: the evaluation stage's promotion (`✓ Model promoted to production via MLflow registry`) is the registry's stage transition. Lab 08's monitoring closes the loop: drift detection triggers the retrain — the weekly cron in the workflow is the scheduled stand-in, but production replaces it with 'drift alert → open retrain pipeline'. Lab 09's validator is already wired in — the workflow's `data-validation` job literally runs `com.mlops.lab09.DataValidationLab`. The architecture reads top-to-bottom: data and code events → validated → trained → evaluated against champion → gated → deployed → monitored → drift re-triggers the loop. The lab gives you each arrow as a Java class."

**Interviewer**: "What's the most common failure you've seen in ML CI/CD, and what does this lab's design do about it?"

**Candidate**: "The 'pipeline is green, model is bad' failure — CI passes because it tests code, not model quality. This lab's answer is structural: model evaluation is a *hard gate*, not a reporting step — the pipeline stops at `Pipeline FAILED at stage: Model Evaluation` if the champion comparison fails, and nothing downstream runs. The second failure: promotion without evidence — the shadow-test stage (`Shadow test passed (1000 requests, 0 errors)`) and the production environment's approval requirement make promotion a deliberate, recorded act. And the third: unmanaged rollback — every deployment versioned, rollback a registry re-tag. Three failure modes, three gates. That's what 'CI/CD for ML' means versus plain CI/CD."

**Interviewer**: "The LeetCode list mentions a pipeline system, version control, and configuration management. How do they map?"

**Candidate**: "Design a Pipeline System covers stage dependencies and parallel execution — the lab's `PipelineStage` graph with `dependencies` and skip logic is the small version; Airflow's DAG (Lab 01) is the large one. Design Version Control System is the model registry angle — versions, diffs, rollbacks — which Lab 03 implements and this lab's rollback job consumes. Design a Configuration Management System is the pipeline-as-code angle: the pipeline definition *is* configuration, stored in git, reviewed in PRs, executed identically in every environment — which is why the lab generates the workflow and Jenkinsfile from code rather than handwriting them in two places that drift apart."
